## 1. 文档目的

本文档用于定义 BridgeAI-Agent 项目的建设背景、业务目标、技术定位、设计原则、系统边界及阶段性成果，为后续总体架构设计、Agent 设计、工具接口设计、RAG 知识库设计、数据架构设计、前后端开发和系统部署提供统一依据。

本文档既是项目立项和技术决策的基础，也是后续团队协作、代码开发、系统验收、版本迭代和内部培训的基准文档。

BridgeAI-Agent 的建设重点不是重新开发一个病害识别模型，也不是构建一个只具备问答能力的聊天机器人，而是在现有桥梁、道路、隧道和智慧工地 AI 能力基础上，建设一个能够理解任务、规划步骤、调用专业工具、管理过程状态、组织工程数据并输出正式成果物的行业智能体平台。

## 2. 项目背景

### 2.1 行业背景

桥梁、公路、隧道及智慧工地等交通基础设施场景具有以下典型特点：

1. 巡检对象数量大、分布范围广，人工检查成本高。
2. 病害类型多样，不同结构、材质、光照和拍摄角度下的视觉差异明显。
3. 现场数据来源复杂，包括无人机影像、车载相机、固定摄像机、检测设备、GIS 数据及人工记录。
4. 检测结果不仅需要识别病害，还需要完成定位、分类、统计、复核、规范引用、处置建议和报告编制。
5. 工程成果要求可追溯、可复核、可审计，不能只输出无法解释的模型结果。
6. 项目通常涉及业主、检测单位、施工单位、监理单位和技术服务单位，多角色协作要求较高。

传统巡检方式主要依赖人工经验，存在效率低、主观差异大、数据难沉淀和报告编制周期长等问题。计算机视觉、无人机、三维重建、知识库和大语言模型的发展，为交通基础设施检测提供了新的技术路径。

但是，单点式 AI 模型通常只能完成某一个环节，例如病害检测、目标分割或文字生成，无法自动完成完整的工程任务。因此，需要从“单模型识别”进一步发展到“任务级智能协同”。

### 2.2 现有基础

BridgeAI-Agent 项目并非从零开始。目前已经具备较为完整的业务和技术基础，包括：

- 现场影像采集能力；
- 无人机和面阵相机数据采集经验；
- 桥梁及道路病害样本积累；
- 图像标注和数据集制作流程；
- YOLO 系列检测与分割模型训练流程；
- 基于 Apple MLX 的本地训练和推理能力；
- 病害识别、统计和结果可视化能力；
- GIS 地图与病害空间定位能力；
- 行业规范和工程知识库建设基础；
- 病害处置建议生成能力；
- Word、PDF 等正式报告自动生成能力；
- 从数据采集、标注、训练、推理到报告输出的完整工作流。

现有系统已经能够按照固定流程完成巡检任务，但主要依赖预先编排的确定性工作流。当任务类型、数据质量、病害类别、项目要求或报告模板发生变化时，仍需要人工判断并调整流程。

因此，下一阶段的重点不是推翻现有系统，而是将已有成熟能力标准化、工具化，并由 Agent 进行统一调度。

## 3. 当前问题与建设必要性

### 3.1 高质量样本获取困难

交通基础设施病害样本需要在真实现场条件下采集。病害分布不均、拍摄条件复杂、标注专业性高，导致样本采集和标注成本远高于普通视觉任务。

当前项目已经积累数千张高价值样本，但从提高模型泛化能力和工程可靠性的角度看，仍需持续扩充以下数据：

- 不同桥型和构件类型；
- 不同病害等级；
- 不同拍摄距离和角度；
- 不同天气、季节和光照条件；
- 容易误检的负样本；
- 少见病害和极端场景；
- 复核后确认的难例；
- 多设备、多项目和多区域数据。

因此，系统必须具备数据闭环能力，让每一次项目执行都能反向促进数据集和模型迭代。

### 3.2 单一模型指标无法代表工程效果

模型总体 mAP、Precision、Recall 等指标只能反映整体测试集表现，不能完全代表真实工程质量。实际项目更关心：

- 某类关键病害是否漏检；
- 是否在特定构件上频繁误检；
- 是否能识别微小裂缝；
- 是否能稳定处理复杂背景；
- 是否能准确关联空间位置；
- 是否能输出可供工程人员复核的证据；
- 是否能够支持正式报告和处置决策。

因此，BridgeAI-Agent 需要建立面向业务场景的分层评测体系，而不是只关注单一模型指标。

### 3.3 现有能力相对分散

现有检测、测量、GIS、知识库、报告生成等能力可以独立运行，但尚未形成统一的工具标准、任务状态和调度机制。

如果继续依赖固定脚本或人工串联，将产生以下问题：

- 新增功能后流程维护成本增加；
- 不同项目难以复用；
- 任务失败后不易恢复；
- 中间结果缺乏统一管理；
- 模型、数据和报告之间难以追溯；
- 难以扩展到多业务线和多 Agent 协同。

### 3.4 工程决策需要知识与证据结合

病害识别只是工程巡检的第一步。最终成果通常还需要结合：

- 病害类型和等级；
- 构件位置；
- 结构形式；
- 行业规范；
- 历史检测记录；
- 专家经验；
- 处治方案；
- 复核意见。

大语言模型适合完成任务理解、信息组织、知识检索和文本生成，但不应替代专业检测工具和人工责任主体。BridgeAI-Agent 需要通过 RAG、工具调用、证据引用和人工复核，将视觉识别、工程知识和正式报告有机结合。

## 4. 项目定位

### 4.1 总体定位

BridgeAI-Agent 定位为：

> 面向桥梁、公路、隧道和智慧工地场景，融合计算机视觉、GIS、行业知识库、任务工作流和大语言模型的交通基础设施行业级 AI Agent 平台。

其核心能力是：

> 理解工程任务，规划执行步骤，调用已有专业工具，管理任务状态，组织检测证据，并输出可复核、可追溯的工程成果。

### 4.2 与传统聊天机器人的区别

BridgeAI-Agent 不以自由问答为主要目标，而以完成真实业务任务为核心。

| 对比项 | 普通聊天机器人 | BridgeAI-Agent |
|---|---|---|
| 主要目标 | 回答问题 | 完成工程任务 |
| 数据来源 | 对话上下文和通用知识 | 项目数据、模型结果、GIS、规范、历史记录 |
| 执行能力 | 以文本生成为主 | 可调用检测、测量、检索、制图和报告工具 |
| 状态管理 | 通常较弱 | 管理完整任务生命周期 |
| 结果形式 | 对话文本 | 结构化结果、图表、地图、Word/PDF 报告 |
| 工程责任 | 通常不涉及 | 必须保留复核、审批和追溯机制 |
| 可解释性 | 依赖模型回答 | 结果关联工具输出、证据和规范依据 |

### 4.3 与现有工作流系统的关系

BridgeAI-Agent 不替代现有稳定工作流，而是在其上增加智能调度层。

现有确定性流程继续承担可靠执行职责，例如：

- 图像预处理；
- YOLO26 推理；
- 病害分割；
- 裂缝测量；
- GIS 坐标处理；
- 数据统计；
- 图表生成；
- Word/PDF 报告生成。

Agent 负责：

- 理解用户目标；
- 判断任务类型；
- 选择合适工具；
- 决定执行顺序；
- 处理异常分支；
- 请求人工复核；
- 汇总和解释结果；
- 组织最终交付物。

## 5. 建设目标

### 5.1 总体建设目标

建设一个能够支持交通基础设施巡检任务自动化执行的 AI Agent 平台，使现有采集、识别、测量、知识检索、统计分析和报告生成能力形成统一、可复用、可扩展的工程系统。

### 5.2 业务目标

1. 降低巡检数据处理和报告编制的人力成本。
2. 缩短从现场采集到成果交付的周期。
3. 提高病害识别、复核和报告输出的一致性。
4. 形成可持续积累的数据资产、模型资产和知识资产。
5. 支持桥梁、公路、隧道和智慧工地等多业务场景。
6. 让每一次项目执行都能为后续模型优化和知识沉淀提供数据。
7. 建立可复制的产品化交付能力，减少一次性项目定制。

### 5.3 技术目标

1. 建立统一的 Agent 调度框架。
2. 将现有成熟能力封装为标准 Tool。
3. 建立可恢复、可追踪的任务工作流。
4. 建立面向项目和任务的状态管理机制。
5. 接入行业规范、检测标准和历史案例知识库。
6. 支持模型、数据集、任务、结果和报告的版本追溯。
7. 支持人工复核、审批和结果修正。
8. 支持本地模型、云端模型及不同大语言模型灵活切换。
9. 为后续 MCP 工具互操作、A2A Agent 协作，以及 LangGraph、Google ADK 等编排框架评估预留接口。
10. 支持本地部署、私有化部署和混合部署。

### 5.4 产品目标

第一阶段形成一个可运行的最小可行产品，完成以下闭环：

1. 用户创建巡检任务；
2. 上传或选择巡检影像；
3. Agent 判断任务类型；
4. 调用病害检测工具；
5. 生成病害清单和统计结果；
6. 调用知识库检索相关规范；
7. 生成处置建议；
8. 提交人工复核；
9. 生成 Word/PDF 报告；
10. 保存任务、模型、证据和报告版本。

## 6. 典型应用场景

### 6.1 无人机桥梁巡检

用户上传无人机采集的桥梁影像，Agent 自动完成：

- 数据完整性检查；
- 图像预处理；
- 病害检测和分割；
- 构件与病害关联；
- GIS 或三维空间定位；
- 病害数量和等级统计；
- 规范条款检索；
- 处治建议生成；
- 人工复核任务创建；
- 正式报告生成。

### 6.2 移动检测车影像处理

系统接收多相机同步采集的桥梁或道路影像，Agent 根据相机编号、时间戳和里程信息进行数据组织，调用检测工具识别病害，并生成按路线、构件和病害类型分类的成果。

### 6.3 历史检测对比

用户选择同一桥梁不同年份的检测任务，Agent 自动对比：

- 病害数量变化；
- 病害面积或长度变化；
- 新增、扩大、稳定和消失的病害；
- 不同模型版本的识别差异；
- 需要重点复核的异常变化。

### 6.4 行业知识辅助

工程人员可以针对某一病害询问：

- 对应规范要求；
- 病害形成原因；
- 风险等级；
- 检测方法；
- 处治方案；
- 类似历史案例。

Agent 必须优先引用内部知识库和有效规范，并明确回答依据。

### 6.5 智慧工地安全巡检

在扩展阶段，系统可复用同一 Agent 框架，接入安全帽识别、明火识别、人员闯入、临边防护和危险源识别等工具，实现智慧工地安全巡检任务自动化。

## 7. 核心设计原则

### 7.1 工具优先

专业能力必须优先由确定性工具完成。大语言模型不得直接替代病害识别、尺寸计算、坐标转换和报告渲染等专业模块。

### 7.2 Agent 负责编排，不重复造轮子

Agent 的核心职责是理解目标、规划任务、调用工具、处理分支和组织结果。已有成熟模块应通过标准接口接入，而不是重新实现。

### 7.3 确定性流程与智能决策结合

对于必须稳定执行的环节，采用固定工作流；对于任务理解、工具选择、异常判断和知识组织等环节，采用 Agent 决策。

### 7.4 人在回路

以下关键环节必须支持人工复核：

- 重大病害确认；
- 低置信度结果；
- 规范适用性判断；
- 病害等级确认；
- 处治建议审核；
- 正式报告签发。

### 7.5 数据资产化

所有项目数据都应按照统一规则沉淀，包括：

- 原始影像；
- 标注数据；
- 模型版本；
- 推理结果；
- 人工修正；
- 难例和负样本；
- 规范引用；
- 报告版本；
- 项目反馈。

### 7.6 全链路可追溯

每一项最终结论都应能够追溯至：

- 原始影像；
- 检测工具；
- 模型版本；
- 推理参数；
- 人工复核记录；
- 知识库来源；
- 报告版本。

### 7.7 模块化与可替换

Agent 框架、语言模型、视觉模型、向量数据库、对象存储、报告引擎和前端框架应保持低耦合，避免被单一厂商或单一技术栈锁定。

### 7.8 安全与权限隔离

项目数据、模型、报告和知识库应按组织、项目和角色进行权限控制。敏感工程数据应优先支持本地或私有化部署。

### 7.9 渐进式演进

项目采用以下演进路线。MCP 用于 Tool 的标准化接入，A2A 用于独立 Agent 服务之间的协作；二者不替代业务任务状态和审计模型。

1. 单 Agent + 多工具；
2. 可恢复工作流；
3. RAG 与项目记忆；
4. 内部 Tool SDK + FastAPI / MCP 标准化适配；
5. 基于 LangGraph 子图或服务边界的多 Agent 专业协作；
6. 当出现跨服务协作、跨框架 Agent 互联或云端 Agent Runtime 需求时，开展 Google ADK 等框架的架构验证；
7. Dify 可作为知识问答、轻量流程和人工运营的低代码应用入口，但不与核心巡检 Workflow 共同管理同一任务状态。

## 8. 系统范围

### 8.1 第一阶段范围

第一阶段重点建设桥梁病害巡检 Agent，范围包括：

- 巡检任务创建；
- 影像上传和管理；
- YOLO26 检测或分割工具接入；
- 推理结果结构化；
- 病害清单生成；
- 行业知识库检索；
- 处置建议生成；
- 人工复核；
- Word/PDF 报告生成；
- 任务日志和版本追踪。

### 8.2 暂不纳入第一阶段的范围

以下能力不作为第一阶段必须交付内容：

- 完全自主的多 Agent 协商；
- 无人工参与的正式检测结论签发；
- 全自动桥梁结构安全评定；
- 大规模实时视频流分析；
- 无人机自主飞行控制；
- 通用型行业大模型训练；
- 覆盖全部道路、隧道和工地场景；
- 替代现有专业检测人员和责任主体。

这些能力可在后续版本中根据数据、业务和合规条件逐步建设。

## 10. 成功标准

BridgeAI-Agent 第一阶段可通过以下标准判断是否达到预期：

### 10.1 功能标准

- 能够完成一次完整的桥梁病害巡检任务；
- 能够自动调用不少于三个专业工具；
- 能够保存任务状态和中间结果；
- 能够处理至少一种异常分支；
- 能够发起人工复核；
- 能够生成结构化病害清单；
- 能够检索并引用行业知识；
- 能够生成正式 Word 或 PDF 报告；
- 能够追溯模型版本、数据来源和复核记录。

### 10.2 工程标准

- Tool 接口统一；
- 任务执行可重试；
- 关键操作有日志；
- 结果具备唯一标识；
- 数据、模型和报告具备版本号；
- 主要模块可独立测试；
- 系统可以在本地开发环境运行；
- 支持后续迁移到服务器或私有云。

### 10.3 业务标准

- 相比纯人工流程，明显减少重复操作；
- 报告生成时间明显缩短；
- 工程人员可以理解和复核 Agent 的执行过程；
- 现有模型、脚本和报告能力得到复用；
- 新项目数据能够沉淀到数据资产体系；
- 能够为后续道路、隧道和智慧工地扩展提供基础。

## 11. 风险与约束

### 11.1 数据风险

- 样本数量和场景覆盖不足；
- 标注标准不一致；
- 部分病害类别样本稀缺；
- 负样本和难例积累不足；
- 不同设备数据分布存在差异。

### 11.2 模型风险

- 低置信度结果被误用；
- 新项目场景导致模型泛化下降；
- 多模型结果不一致；
- 模型升级后历史结果不可比。

### 11.3 Agent 风险

- Agent 错误选择工具；
- 执行顺序不合理；
- 大语言模型产生无依据结论；
- 任务上下文过长导致信息遗漏；
- 工具调用失败后无法正确恢复。

### 11.4 工程与合规风险

- 工程数据涉及保密要求；
- 正式检测结论需要资质人员签署；
- 规范版本可能发生变化；
- 自动生成建议不得直接替代专业责任判断；
- 系统必须保留人工复核和审计记录。

## 13. 本章结论

BridgeAI-Agent 的核心价值，不是单纯增加一个大语言模型入口，而是把已经跑通的巡检流程、视觉模型、GIS、知识库和报告系统，升级为一个可理解任务、可调用工具、可管理状态、可人工复核、可持续迭代的行业智能体平台。

项目应坚持“专业工具负责执行、Agent 负责调度、人工负责关键复核、数据持续形成资产”的总体思路。

第一阶段应优先完成单 Agent、多工具、可追溯任务闭环，不宜一开始就追求复杂的多 Agent 系统。待 Tool SDK、任务状态、数据结构和评测体系稳定后，再逐步引入 MCP 工具互操作、A2A Agent 协作和多 Agent 能力；Google ADK 应作为经验证的编排框架选项，而不是既定的替换目标。
