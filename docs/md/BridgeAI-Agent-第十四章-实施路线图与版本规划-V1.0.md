## 14.1 本章目标

本章是 BridgeAI-Agent 第一套正式目录的收官章节，目标是把前十三章形成的架构、Agent、Tool、Workflow、RAG、Memory、数据、MCP、Prompt、前后端、模型评测、部署监控和安全设计，转化为可执行、可验收、可迭代的实施路线图。

前十三章回答“系统应该是什么样”。本章回答“研发团队应如何把它落地”：

- 哪些能力进入第一阶段，哪些能力延后；
- 每个版本交付什么，不交付什么；
- 每个里程碑达到什么状态才算通过；
- 文档、代码、数据、模型、Prompt、Schema、Tool、部署和评测如何一起发布；
- 风险、依赖、人员责任和验收门禁如何管理；
- 如何从正式架构文档拆解研发 Backlog 和工程 Issue。

本章不把尚未实现的软件能力描述为已经完成。当前完成的是 V1.0 架构文档基线，后续工程实现应按本章路线图逐步推进。

## 14.2 路线图定位与边界

BridgeAI-Agent 的第一阶段重点是桥梁与道路巡检 AI Agent，核心闭环是：

1. 创建巡检项目和任务；
2. 上传或选择影像、视频、点云或其他检测资料；
3. Agent 理解任务目标并规划执行步骤；
4. 调用病害检测、分割、测量、统计、知识检索和报告生成 Tool；
5. 形成结构化病害清单、证据链、处置建议和报告草稿；
6. 进入人工复核、修正、审批和正式报告签发；
7. 沉淀项目数据、模型反馈、难例、规范引用和审计记录。

本路线图聚焦产品化落地，不替代项目管理制度、商务计划或人员排班。它定义技术实施顺序、版本边界、质量门禁和交付物，使研发工作能够从“设计文档”平滑转入“可运行系统”。

第一阶段不是一次性做成完整平台，而是做出一个可被工程团队使用、可复核、可追溯、可部署、可扩展的最小可用闭环。复杂多 Agent 协同、A2A、无人机自主飞行控制、大规模实时视频分析和全自动结构安全评定，不作为第一阶段成功的必要条件。

## 14.3 总体实施原则

第一阶段实施遵循八项原则。

| 原则 | 含义 | 对实施的约束 |
|---|---|---|
| 先闭环再扩张 | 先跑通一类核心业务，再横向扩展 | 优先桥梁与道路巡检，不同时铺开多个行业场景 |
| 证据链优先 | 所有结论可追溯 | 任何版本不得绕过 Artifact、模型、Prompt、复核和报告版本记录 |
| 工具优先 | 专业能力由 Tool 执行 | 大模型负责调度、判断和组织，不替代检测模型和测量工具 |
| 人在回路 | 关键结论需人工确认 | 正式报告签发前必须支持复核和审批 |
| 版本可验收 | 版本由能力集合定义 | 每个版本都有进入条件、交付物和退出标准 |
| 架构渐进 | 复杂能力按接口成熟度引入 | MCP、A2A、多 Agent 和云端框架不抢占第一阶段主线 |
| 安全默认 | 数据、模型、密钥和报告默认受控 | 研发、测试、部署均不得泄露敏感工程资料 |
| 可回滚可复盘 | 失败时能够恢复和解释 | 版本发布必须保留配置、模型、Prompt、Schema 和数据迁移记录 |

这些原则用于处理取舍。例如，当“更智能的自动推理”和“更可靠的人工复核链”发生冲突时，第一阶段优先后者；当“快速接入更多工具”和“统一 Tool SDK 契约”发生冲突时，第一阶段优先契约稳定。

## 14.4 版本体系与发布语义

BridgeAI-Agent 采用“文档基线 + 工程版本 + 能力门禁”的版本体系。

| 版本 | 定位 | 主要目标 | 发布性质 |
|---|---|---|---|
| V0.1 | 文档与架构基线 | 完成十四章正式设计文档和研发拆解依据 | 设计基线 |
| V0.2 | 工程骨架 | 建立后端、前端、Tool、Agent、Workflow 的可运行骨架 | 内部开发版 |
| V0.3 | Tool SDK 闭环 | 接入首批专业工具并形成统一调用规范 | 工具闭环版 |
| V0.4 | Workflow/Agent 闭环 | 完成单 Agent、多工具、可恢复任务流 | 核心能力版 |
| V0.5 | RAG/Memory/Prompt 闭环 | 建立证据检索、项目记忆和结构化输出 | 智能增强版 |
| V0.6 | 工作台闭环 | 支持任务、复核、证据和报告的 Web 操作 | 试用工作台版 |
| V0.7 | 模型与评测闭环 | 建立模型资产、评测集、发布门禁和反馈机制 | 质量门禁版 |
| V0.8 | 部署与安全闭环 | 完成本地/内网部署、监控、备份和安全基线 | 试点部署版 |
| V1.0 | 第一阶段正式版 | 完成桥梁与道路巡检 AI Agent 可交付闭环 | 第一阶段交付版 |
| V1.1 | 道路巡检增强 | 扩展道路场景、效率和批处理能力 | 增强版 |
| V1.2 | 多项目与运维增强 | 增强多项目、多租户、治理和运营能力 | 平台化增强版 |
| V2.0 | 多 Agent 与跨系统协作 | 引入专业 Agent、A2A 和更复杂生态集成 | 架构演进版 |

版本号不能只代表日期。只有当对应能力、测试、文档、部署说明、数据迁移、回滚方案和验收记录同时满足要求，才能发布该版本。

## 14.5 V0.1 文档与架构基线

V0.1 的目标是形成可被研发团队执行的架构基线。当前十四章正式文档完成后，即可作为 V0.1 文档基线。

交付物：

| 类别 | 交付物 | 验收标准 |
|---|---|---|
| 正式文档 | 第一章至第十四章 Markdown | 目录完整、命名统一、聚焦桥梁与道路巡检 |
| 规格说明 | 每个后续章节的设计 Spec | 范围、非范围、验证要求明确 |
| 实施计划 | 每个后续章节的 Plan | 可追踪到正式文档和验证项 |
| README | 仓库说明和文档清单 | 正式主线清晰，不与历史参考目录混淆 |
| 架构决策 | 各章 ADR | 决策、背景和后果可追溯 |

V0.1 不要求软件已经可运行，但要求研发进入下一阶段时不再反复争论核心边界：第一阶段做桥梁与道路巡检闭环；智慧工地、复杂多 Agent 和跨组织协作作为后续演进。

退出标准：

- 十四章正式文档全部存在；
- README 文档清单完整；
- 第一阶段范围和不纳入范围明确；
- 每章关键 ADR 可被引用；
- 可以从文档拆解工程 Backlog。

## 14.6 V0.2 工程骨架与本地运行

V0.2 的目标是建立可以启动、可以联调、可以持续演进的工程骨架。

主要任务：

| 模块 | P0 工作 | 验收 |
|---|---|---|
| 后端 | 建立 FastAPI 应用、配置、认证占位、健康检查、OpenAPI | 本地可启动，健康接口可用 |
| 前端 | 建立 Vue + TypeScript 工作台骨架 | 能打开首页、任务列表和占位详情页 |
| Agent | 建立 Agent Runner 接口和任务上下文对象 | 可接收任务并返回结构化状态 |
| Workflow | 建立任务状态机和 Checkpoint 存储接口 | 可创建、推进、失败和恢复任务状态 |
| Tool SDK | 建立 Tool Manifest、参数 Schema、结果 Schema | 可注册示例 Tool 并通过统一入口调用 |
| 数据 | 建立 PostgreSQL 基础表、对象存储占位、迁移脚本 | 本地迁移可重复执行 |
| 部署 | 建立本地运行说明和开发环境变量模板 | 新环境可按说明启动基础服务 |

V0.2 不追求真实病害识别效果，而是让所有模块拥有稳定入口。此阶段若接口经常变化是正常的，但必须通过 Schema、迁移记录和变更说明留下痕迹。

退出标准：

- 后端、前端、Agent、Workflow、Tool SDK 可在本地启动；
- 创建任务、查看任务状态和调用示例 Tool 的最小链路可运行；
- 工程目录、配置、日志和测试入口清晰；
- 不把密钥、真实工程数据或大模型凭据提交到仓库。

## 14.7 V0.3 Tool SDK 与首批工具闭环

V0.3 的目标是让现有专业能力通过统一 Tool SDK 进入 Agent 编排体系。

首批工具建议：

| 工具 | 优先级 | 能力 | 备注 |
|---|---|---|---|
| 影像导入与完整性检查 Tool | P0 | 校验文件、元数据、重复和缺失 | 是所有后续识别的入口 |
| 病害检测/分割 Tool | P0 | 输出病害类别、位置、置信度、掩膜或框 | 可先接入已有 YOLO26 能力 |
| 病害统计 Tool | P0 | 汇总数量、面积、长度、等级和构件分布 | 服务报告与复核 |
| Artifact 管理 Tool | P0 | 保存原图、结果图、JSON、表格和报告中间件 | 形成证据链 |
| 报告生成 Tool | P0 | 输出 Word/PDF 报告草稿 | 第一阶段闭环关键 |
| GIS/里程映射 Tool | P1 | 关联路线、桩号、坐标或构件 | 道路场景增强 |
| 历史对比 Tool | P1 | 对比多期病害变化 | 可在 V1.1 强化 |

Tool SDK 必须统一描述：

- `tool_id`、版本、能力、输入 Schema、输出 Schema；
- 超时、重试、幂等、错误码和资源限制；
- Artifact 输入输出；
- 权限、风险等级和审计字段；
- 可观测字段和评测样例。

退出标准：

- P0 工具至少形成一个真实或半真实数据闭环；
- Agent 不直接调用散装脚本，而是通过 Tool Registry 和 Tool Executor 调用；
- 每次 Tool 调用都有输入、输出、错误、耗时、版本和 Artifact 记录；
- Tool 失败能够进入 Workflow 异常分支，而不是中断后丢失状态。

## 14.8 V0.4 Workflow/Agent 最小闭环

V0.4 的目标是完成单 Agent、多工具、可恢复任务闭环。

最小任务流：

| 节点 | 输入 | 输出 | 关键门禁 |
|---|---|---|---|
| 任务理解 | 用户目标、项目资料 | 任务类型、执行计划 | 不确定时进入澄清 |
| 数据检查 | 影像和元数据 | 数据质量报告 | 缺失严重则阻断 |
| 工具执行 | 检测/统计工具 | 病害候选结果 | Tool 版本可追溯 |
| 结果汇总 | 候选病害、统计结果 | 病害清单 | 低置信度标记 |
| 知识检索 | 病害类型、构件、规范范围 | 引用依据 | 引用必须可追溯 |
| 建议生成 | 病害清单、规范证据 | 处置建议草稿 | 不替代专业判断 |
| 人工复核 | 清单、证据、建议 | 确认/修正记录 | 正式结论前强制 |
| 报告生成 | 复核结果、模板 | Word/PDF 草稿 | 报告版本可追溯 |

V0.4 的重点不是让模型回答更华丽，而是让任务状态可管理。每个节点都应有状态、输入、输出、错误、重试策略和审计记录。

退出标准：

- 一次桥梁病害巡检任务可以从创建推进到报告草稿；
- 至少一个节点支持失败恢复；
- Agent 决策和 Tool 调用均可追踪；
- 人工复核是状态机的一部分，不是线下补充动作。

## 14.9 V0.5 RAG、Memory 与 Prompt 证据链闭环

V0.5 的目标是把行业知识、项目上下文和结构化输出接入主流程，使 Agent 的结论有依据、有记忆、有格式约束。

核心能力：

| 能力 | P0 要求 | 验收 |
|---|---|---|
| RAG 知识库 | 接入规范、检测标准、历史案例或企业知识 | 回答能返回来源、版本和片段 |
| Project Memory | 保存项目基本信息、任务上下文和复核偏好 | 同项目多轮任务可复用上下文 |
| Prompt Registry | 管理 System、Task、Tool、RAG、Review、Report Prompt | Prompt 有版本和变更记录 |
| JSON Schema | 约束病害清单、证据、建议和报告字段 | 输出可验证，错误可重试 |
| 引用链 | 连接结论、规范、Artifact、模型和复核 | 报告关键结论可追溯 |

本阶段必须避免“看似智能但无依据”的输出。RAG 命中不足、规范冲突、Memory 不确定或 Schema 校验失败时，应明确进入降级、澄清或人工复核路径。

退出标准：

- Agent 生成处置建议时能展示知识来源；
- Project Memory 能影响同一项目的后续任务，但不会覆盖事实证据；
- Prompt 和 Schema 均可版本化；
- 报告草稿中的关键结论能够反查到规范引用、检测结果和人工复核记录。

## 14.10 V0.6 前后端工作台与人工复核

V0.6 的目标是让工程人员能够通过 Web 工作台完成任务操作，而不是依赖命令行或研发人员代跑。

第一阶段工作台应包含：

| 区域 | P0 能力 | P1 能力 |
|---|---|---|
| 项目与任务 | 创建项目、创建任务、查看状态 | 批量任务、模板任务 |
| 资料管理 | 上传影像、查看 Artifact | 地图/里程视图 |
| 执行过程 | 查看节点状态、错误和重试 | 实时事件流详情 |
| 病害复核 | 查看病害、证据图、置信度、修改结论 | 多人协同复核 |
| 知识引用 | 查看规范来源和引用理由 | 引用对比和版本差异 |
| 报告 | 预览、导出、签发记录 | 模板管理和批量报告 |
| 管理诊断 | 查看版本、健康、任务、审计摘要 | 权限策略可视化 |

人工复核不是“产品体验锦上添花”，而是第一阶段的安全阀。重大病害、低置信度、规范冲突、报告签发和模型异常必须能在工作台中被看见、修正和记录。

退出标准：

- 非研发用户可完成核心任务操作；
- 人工复核结果能回写数据库并影响报告；
- 前端不直连数据库、对象存储、Qdrant 或 MCP Server；
- 错误、阻断和降级状态在界面上明确可见。

## 14.11 V0.7 模型管理、评测和发布门禁

V0.7 的目标是把模型从“能跑”治理为“可发布、可回滚、可比较”。

模型治理范围：

| 对象 | 管理要求 |
|---|---|
| 视觉模型 | 权重、类别集、训练数据、评测集、推理参数、硬件环境 |
| 大语言模型 | 模型供应商、本地/云端模式、上下文窗口、成本、延迟、安全限制 |
| Embedding/Reranker | 语料版本、向量维度、索引版本、召回评测 |
| Prompt/Schema | 版本、适用节点、评测样例、失败样例 |
| 工具模型组合 | 模型 + Tool + Prompt + Schema 的组合版本 |

评测不能只看单一准确率。第一阶段至少覆盖：

- 病害识别精度、召回、误报和漏报；
- 低置信度样本和难例识别；
- RAG 引用准确性；
- 结构化输出 Schema 通过率；
- 人工复核修改率；
- 报告关键字段一致性；
- 端到端任务成功率、耗时和失败恢复能力。

退出标准：

- 每个生产候选模型都有评测报告；
- 模型、Prompt、Schema 和 Tool 组合可以固定版本；
- 不通过评测门禁的模型不得进入正式任务；
- 线上反馈和人工修正可以进入数据闭环。

## 14.12 V0.8 部署、监控、安全和恢复演练

V0.8 的目标是把系统从“可开发运行”推进到“可试点部署”。

关键能力：

| 主题 | P0 要求 |
|---|---|
| 部署 | 支持本地或内网部署，服务拓扑清晰 |
| 配置 | 环境变量、密钥、证书和服务地址分离 |
| 监控 | API、Workflow、Tool、Model、RAG、Memory、对象存储和数据库有健康指标 |
| 日志 | 任务、工具、模型、报告和错误具备关联 ID |
| 审计 | 报告签发、复核、下载、权限拒绝和高风险 Tool 调用入审计 |
| 备份 | PostgreSQL、对象存储、向量索引、配置和报告可恢复 |
| 安全 | 权限、RLS、MCP scope、上传下载、密钥和供应链检查 |
| 演练 | 至少完成一次恢复演练和一次失败回滚演练 |

V0.8 不要求大规模 Kubernetes 生产集群，但必须证明在本地/内网试点环境中，系统能够被部署、观察、恢复和安全控制。

退出标准：

- 试点环境可按 Runbook 部署；
- 关键服务健康可见；
- 备份恢复演练有记录；
- 发布、回滚和异常响应流程可执行；
- 敏感数据、密钥和权限边界通过检查。

## 14.13 V1.0 第一阶段正式交付范围

V1.0 是第一阶段正式交付版。它应证明 BridgeAI-Agent 已经具备桥梁与道路巡检 AI Agent 的完整产品闭环。

V1.0 必须交付：

| 类别 | 必须能力 |
|---|---|
| 项目任务 | 项目创建、任务创建、资料导入、状态跟踪 |
| Agent 编排 | 单 Agent 多工具规划、执行、异常处理和恢复 |
| Tool 能力 | 影像检查、病害检测/分割、统计、Artifact、报告生成 |
| 数据资产 | PostgreSQL/PostGIS、对象存储、向量库、审计和版本记录 |
| RAG/Memory | 行业知识检索、项目上下文、引用证据和结构化输出 |
| 人工复核 | 病害复核、建议审核、报告签发和修正记录 |
| 模型治理 | 模型版本、评测报告、发布门禁、回滚和反馈闭环 |
| 前端工作台 | 任务、证据、复核、报告、健康和审计摘要 |
| 部署运维 | 本地/内网部署、监控、日志、告警、备份和恢复 |
| 安全合规 | 认证授权、权限隔离、MCP/Tool 安全、敏感数据保护 |

V1.0 成功标准：

- 能完成至少一个端到端桥梁或道路巡检任务样例；
- 能生成结构化病害清单和可复核报告草稿；
- 关键结论可追溯到影像、模型、Tool、Prompt、RAG、Memory 和人工复核；
- 正式报告签发不绕过人工复核；
- 任务失败、模型异常、RAG 不可用和权限异常有清晰处理路径；
- 系统可在本地或内网环境部署并完成备份恢复演练；
- 文档、接口、Schema、Prompt、模型和部署版本保持一致。

## 14.14 V1.1 道路巡检增强与效率优化

V1.1 在 V1.0 稳定后启动，重点扩展道路巡检细分能力和批处理效率。

建议方向：

| 方向 | 能力 | 前置条件 |
|---|---|---|
| 道路病害增强 | 裂缝、坑槽、车辙、沉陷、修补、标线等分类增强 | V1.0 病害数据闭环稳定 |
| 里程与路线关联 | 桩号、路线、车道、方向和采集时序关联 | GIS/里程数据质量可控 |
| 批处理优化 | 多任务队列、断点续跑、批量报告 | Workflow 和 Worker 稳定 |
| 历史对比 | 多期病害变化和处治跟踪 | 数据版本和构件/路段 ID 稳定 |
| 报告模板增强 | 道路、桥梁、专项检查模板 | V1.0 报告生成链稳定 |

V1.1 不应改变 V1.0 的核心状态模型和证据链，只在稳定接口之上扩展道路场景、批处理和效率优化。

## 14.15 V1.2 多项目、多租户与运维增强

V1.2 的目标是从单项目/试点交付走向多项目、多组织和持续运营。

建议方向：

| 方向 | 能力 | 风险控制 |
|---|---|---|
| 多项目治理 | 项目模板、权限继承、跨项目统计 | 强化 RLS 和审计 |
| 多租户隔离 | 组织、项目、角色、数据域隔离 | 避免对象存储和向量库串租 |
| 运营后台 | 任务队列、失败重跑、版本诊断、容量监控 | 高风险动作需审批 |
| 数据治理 | 标注回流、难例库、数据质量评分 | 防止污染评测集 |
| 模型灰度 | 按项目、路线、病害类型灰度 | 保留回滚和对照组 |
| 成本与容量 | 推理资源、存储增长、队列时延统计 | 建立容量阈值 |

V1.2 的判断标准不是功能数量，而是能否让多个项目稳定共存、可运营、可审计、可升级。

## 14.16 V2.0 多 Agent、A2A 与跨系统协作

V2.0 是架构演进阶段，只有在 V1.0 至 V1.2 的接口、状态、Tool、数据和评测体系稳定后才适合推进。

V2.0 可考虑：

| 能力 | 说明 | 前置条件 |
|---|---|---|
| 专业 Agent 拆分 | 检测 Agent、报告 Agent、知识 Agent、质检 Agent | 单 Agent 职责边界已稳定 |
| A2A 协作 | 独立 Agent 服务之间交换任务、状态和结果 | 任务状态、权限、审计和协议稳定 |
| MCP 生态扩展 | 接入更多标准 MCP Tool 和外部系统 | MCP Gateway、scope 和 Tool Registry 稳定 |
| 跨系统集成 | 与已有巡检、资产、GIS、OA 或档案系统连接 | 外部系统接口和数据权责明确 |
| 云端 Agent Runtime 验证 | 评估 Google ADK 等框架 | 本地核心能力可替换、可回滚 |
| 多模态实时协作 | 视频流、语音、现场移动端协作 | 数据吞吐、实时性和责任边界成熟 |

V2.0 不应推翻前期架构，而应以稳定的 Tool、Workflow、数据、审计和模型治理为底座。多 Agent 的目标是专业协作和规模化，不是为了增加复杂度。

## 14.17 不纳入第一阶段的能力

以下能力不作为 V1.0 必须交付内容：

| 能力 | 延后原因 | 可能版本 |
|---|---|---|
| 完全自主多 Agent 协商 | 状态、责任和审计复杂度高 | V2.0 |
| A2A 跨 Agent 协议正式落地 | 需等待单 Agent 和 Tool 边界稳定 | V2.0 |
| 无人工参与的正式报告签发 | 工程责任和合规风险高 | 不建议作为近期目标 |
| 全自动桥梁结构安全评定 | 需要结构计算、检测规范和专家责任链 | 独立专项 |
| 大规模实时视频流分析 | 算力、延迟和场景复杂度高 | V1.2/V2.0 |
| 无人机自主飞行控制 | 涉及硬件、空域、安全和现场责任 | 独立系统 |
| 通用行业大模型训练 | 成本高，数据量和评测体系要求高 | 长期研究 |
| 覆盖全部道路、隧道、工地场景 | 会稀释第一阶段闭环 | 分场景规划 |
| 替代专业检测人员和责任主体 | 不符合工程责任边界 | 不纳入 |

排除这些能力不是降低愿景，而是保护第一阶段真正落地。一个可用、可信、可追溯的桥梁道路巡检 Agent，比一个范围过大但无法验收的平台更有价值。

## 14.19 里程碑验收与质量门禁

第一阶段建议采用四个综合里程碑。

| 里程碑 | 覆盖版本 | 验收重点 | 不通过处理 |
|---|---|---|---|
| M1 架构与骨架通过 | V0.1-V0.2 | 文档完整、工程可启动、接口边界清晰 | 冻结扩展需求，补齐骨架和接口 |
| M2 核心闭环通过 | V0.3-V0.4 | Tool、Agent、Workflow 可完成最小任务 | 优先修复状态机、Tool 契约和错误恢复 |
| M3 智能与工作台通过 | V0.5-V0.6 | RAG/Memory/Prompt 与人工复核可用 | 暂停新增模型能力，补证据链和复核链 |
| M4 试点交付通过 | V0.7-V1.0 | 模型评测、部署安全、备份恢复、端到端验收 | 禁止正式发布，进入回归和复盘 |

每个里程碑至少包含以下质量门禁：

| 门禁 | 要求 |
|---|---|
| 功能门禁 | P0 场景通过端到端测试 |
| 数据门禁 | 数据迁移可重复执行，关键数据可追溯 |
| 模型门禁 | 候选模型有评测报告和回滚方案 |
| Prompt/Schema 门禁 | 结构化输出通过校验，失败可重试 |
| Tool 门禁 | Tool 版本、输入、输出、错误和 Artifact 可审计 |
| 安全门禁 | 权限、密钥、上传下载、MCP scope 和审计通过检查 |
| 部署门禁 | 可部署、可监控、可备份、可恢复 |
| 文档门禁 | README、接口、Runbook、变更记录同步 |

门禁不通过时，不应通过“口头说明”强行发布。可以降级为内部演示版，但不能标记为 V1.0 正式交付。

## 14.20 风险、依赖与决策检查点

主要风险如下。

| 风险 | 影响 | 预防措施 | 触发后的处理 |
|---|---|---|---|
| 数据样本不足 | 模型评测和报告可信度不足 | 先建立样例数据集和难例库 | 限制发布范围，补采或标注 |
| 工具接口不稳定 | Agent 和 Workflow 频繁返工 | 先固化 Tool Manifest 和 Schema | 暂停新工具，修订契约 |
| 任务状态过粗 | 失败恢复和审计困难 | 按节点记录输入输出和错误 | 返工 Workflow 状态模型 |
| RAG 引用质量不足 | 建议不可采信 | 建立知识来源、版本和召回评测 | 降级为人工查阅辅助 |
| Prompt 输出不稳定 | 报告和复核成本上升 | Schema 校验、重试和样例评测 | 回滚 Prompt 版本 |
| 前端复核体验弱 | 工程人员无法高效使用 | 早期引入真实复核流程演示 | 优先优化复核，不扩展新页 |
| 部署环境差异 | 试点环境不可复现 | 标准化配置、Runbook 和健康检查 | 固化环境矩阵并回归 |
| 安全边界不清 | 数据泄露或越权 | 最小权限、RLS、审计和密钥隔离 | 阻断发布并进行安全复盘 |
| 范围蔓延 | 第一阶段无法收口 | 维护不纳入范围清单 | 进入变更评审 |

关键决策检查点：

| 检查点 | 时间 | 决策问题 |
|---|---|---|
| D1 | V0.2 结束 | 工程骨架是否足够稳定，可以接入真实工具 |
| D2 | V0.3 结束 | Tool SDK 是否成为唯一工具接入路径 |
| D3 | V0.4 结束 | Workflow 状态机是否支撑失败恢复和审计 |
| D4 | V0.5 结束 | RAG/Memory/Prompt 是否能产出可追溯证据 |
| D5 | V0.6 结束 | 工程人员是否能通过工作台完成复核 |
| D6 | V0.7 结束 | 模型评测和发布门禁是否足以支撑试点 |
| D7 | V0.8 结束 | 部署、安全和恢复是否满足内网试点 |
| D8 | V1.0 前 | 是否具备正式交付条件 |

## 14.21 研发节奏与文档治理

建议采用“小步快跑 + 版本门禁”的研发节奏：

| 节奏 | 建议 |
|---|---|
| 迭代周期 | 1 至 2 周一个内部迭代 |
| 版本评审 | 每个 V0.x 结束做一次轻量评审 |
| 演示节奏 | 至少每两个迭代演示一次端到端流程 |
| 文档同步 | 架构、接口、Schema、Prompt、Runbook 变更随版本同步 |
| 复盘机制 | 失败、回滚、模型退化和重大需求变更必须复盘 |

文档治理规则：

- 正式架构文档保存在 `docs/md`；
- 规格说明保存在 `docs/superpowers/specs`；
- 实施计划保存在 `docs/superpowers/plans`；
- README 只描述当前正式主线和可确认状态；
- 架构变更必须补充 ADR 或修订记录；
- Prompt、Schema、Tool Manifest、模型和部署配置必须具备版本号；
- 已签发报告、审计记录和关键 Artifact 不得原地覆盖。

当研发发现文档与实现冲突时，应按以下顺序处理：

1. 判断冲突是否影响安全、证据链、人工复核或数据结构；
2. 若影响核心边界，先发起架构决策更新；
3. 若仅是实现细节差异，在对应章节或 README 中记录修订；
4. 版本发布前完成文档、代码、测试和部署说明同步。

## 14.24 架构决策记录

### ADR-014-001：V1.0 聚焦桥梁与道路巡检闭环

**状态：** Accepted

**背景：** 项目第一阶段需要避免场景过宽导致无法验收。

**决定：** V1.0 聚焦桥梁与道路巡检 AI Agent，优先完成任务、Tool、Workflow、RAG、Memory、人工复核、报告和部署闭环。

**后果：** 智慧工地、隧道、无人机控制和复杂多 Agent 协作不进入第一阶段正式范围，但保留架构可复用性。

### ADR-014-002：采用 V0.1 至 V1.0 的阶段化交付

**状态：** Accepted

**背景：** BridgeAI-Agent 涉及多模块协同，若直接定义一个大版本，容易出现集成后期集中失控。

**决定：** 第一阶段拆分为 V0.1 至 V1.0，并为每个阶段设置进入条件、交付物和退出标准。

**后果：** 版本管理更细，但风险暴露更早，研发和验收更可控。

### ADR-014-003：版本发布必须绑定文档、Schema、Prompt、Tool、模型和部署

**状态：** Accepted

**背景：** AI Agent 系统的行为由代码、模型、Prompt、Schema、Tool 和数据共同决定，单独发布代码无法解释系统行为变化。

**决定：** 每个可验收版本必须记录代码、文档、Schema、Prompt、Tool、模型、数据迁移和部署配置版本。

**后果：** 发布记录更复杂，但可追溯、可回滚和可复盘。

### ADR-014-004：第一阶段以本地/内网试点为交付优先级

**状态：** Accepted

**背景：** 巡检数据和工程报告具有敏感性，且第一阶段更需要快速形成可控试点。

**决定：** V1.0 优先支持本地或内网私有化部署，云端和大规模集群作为后续扩展。

**后果：** 自动扩缩和跨地域能力不是第一阶段重点，但数据安全和试点落地更稳。

### ADR-014-005：人工复核是正式结论发布的硬门禁

**状态：** Accepted

**背景：** 病害等级、处置建议和正式报告涉及工程责任，AI 输出不能替代责任主体。

**决定：** V1.0 中重大病害、低置信度结果、处置建议和正式报告签发必须支持人工复核记录。

**后果：** 端到端自动化比例受到限制，但交付结果更符合工程责任边界。

### ADR-014-006：优先建设证据链和审计链，再扩大自动化范围

**状态：** Accepted

**背景：** 巡检 Agent 的可信度取决于结论是否能被追溯，而不是回答是否流畅。

**决定：** V0.3 至 V1.0 的核心门禁优先检查 Artifact、模型、Tool、Prompt、RAG、Memory、复核和报告的证据链。

**后果：** 一些增强功能会延后，但系统可信度和可验收性更高。

### ADR-014-007：V1.1/V1.2 只能在 V1.0 门禁通过后启动

**状态：** Accepted

**背景：** 道路增强、多项目、多租户和运维平台化会增加系统复杂度。

**决定：** 未通过 V1.0 端到端、模型评测、复核、部署、安全和恢复门禁前，不启动大规模 V1.1/V1.2 开发。

**后果：** 后续增强节奏更稳，避免基础不牢时横向扩张。

### ADR-014-008：A2A 和多 Agent 能力延后到 V2.0

**状态：** Accepted

**背景：** 多 Agent 协作需要稳定的任务状态、权限、审计、协议和责任边界。

**决定：** 第一阶段不建设完全自主多 Agent 协商；A2A 和专业 Agent 拆分作为 V2.0 架构演进方向。

**后果：** V1.0 保持单 Agent 多工具闭环，系统更容易实现和验收；V2.0 具备更清晰的演进前置条件。
