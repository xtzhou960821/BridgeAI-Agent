# BridgeAI-Agent Artifact Image Ingestion and Quality Design

## 1. Goal

Replace the V0.2 string-only Artifact input and constant image-quality result
with one real, locally runnable image path: upload one JPEG or PNG, persist its
metadata in PostgreSQL, store its bytes behind an Artifact storage interface,
bind it to a task, verify it inside LangGraph, and report explainable technical
image-quality metrics in the workbench.

This is the first V0.3 Tool and Artifact slice. It is deliberately limited to
one image per task so the product does not imply that the current graph processes
all members of an Artifact list when it only operates on the first reference.

## 2. Confirmed Decisions

1. Use PostgreSQL for Artifact metadata and a local filesystem adapter for bytes.
2. Hide storage behind an `ArtifactStore` interface so a later MinIO adapter does
   not change the API, task model, or Workflow contract.
3. Support exactly one JPEG or PNG image per newly created task.
4. Integrate upload directly into the existing task-creation form; users no
   longer type Artifact IDs.
5. Separate upload integrity checks from task-time technical quality analysis.
6. Treat a low-quality image as a successful analysis result, not an execution
   failure.
7. Keep legacy tasks and run history readable without inventing Artifact rows.
8. Do not add an Artifact library, deletion, replacement, batch processing,
   MinIO, video, disease detection, or image enhancement in this slice.

## 3. Architecture

```text
Vue task-creation form
  -> POST /api/v1/artifacts
  -> ArtifactService
       -> validate size, signature, and image decoding
       -> calculate SHA-256, byte size, MIME type, width, and height
       -> LocalArtifactStore atomically writes the file
       -> ArtifactRepository persists PostgreSQL metadata
  <- Artifact response with ID, metadata, and controlled content URL
  -> POST /api/v1/tasks with exactly one Artifact ID
  -> TaskService verifies that the Artifact is real and ready
  -> LangGraph task run
       -> data_check verifies the persisted Artifact and stored file
       -> image_quality_check opens the real image through ArtifactStore
       -> ImageQualityAnalyzer returns metrics, thresholds, and reasons
  <- persisted business run, Workflow snapshot, and Tool result
```

The BridgeAI business database remains authoritative for Artifact identity and
metadata. The storage adapter remains authoritative for the bytes. LangGraph
checkpoints contain references and JSON-safe summaries only; they never contain
binary image data, absolute paths, open file handles, or storage clients.

## 4. Component Boundaries

### 4.1 Artifact Domain Object

`ArtifactRecord` describes one immutable uploaded image:

- Artifact ID;
- original filename for display only;
- storage key;
- SHA-256 checksum;
- byte size;
- verified MIME type;
- decoded width and height;
- readiness status;
- UTC creation time.

It contains no binary data and exposes no absolute filesystem path.

### 4.2 ArtifactRepository

The repository owns PostgreSQL SQL and mapping for Artifact metadata. It does
not open files, decode images, know FastAPI request objects, or execute quality
analysis.

### 4.3 ArtifactStore

The storage interface provides narrowly scoped operations to stage, finalize,
open, inspect, and remove a file created by the current operation. The first
implementation is `LocalArtifactStore`. A later S3-compatible implementation
can replace it without changing Artifact IDs or caller contracts.

### 4.4 ArtifactService

The application service coordinates the upload stream, validation, storage,
metadata persistence, lookup, and task-binding validation. It owns compensating
cleanup when a known failure occurs between file creation and database insert.

### 4.5 ImageQualityAnalyzer

The analyzer is a deterministic, side-effect-free technical analysis component.
It accepts decoded image content and a threshold configuration, then returns a
JSON-safe result. It does not query PostgreSQL, access HTTP state, or infer bridge
diseases.

### 4.6 image_quality_check Tool

The Tool handler resolves an Artifact through injected service interfaces, opens
the real image, calls `ImageQualityAnalyzer`, and returns the standard Tool SDK
result. The Tool never accepts an arbitrary local path from the user.

## 5. PostgreSQL Model

Migration `0005_artifacts.sql` creates `inspection_artifacts`.

| Column | Type | Constraint and purpose |
|---|---|---|
| `artifact_id` | `TEXT` | Primary key; backend-generated `art_...` identity |
| `original_filename` | `TEXT` | Nonblank display name; never used as a path |
| `storage_key` | `TEXT` | Unique, nonblank relative key generated by the backend |
| `sha256` | `TEXT` | Exactly 64 lowercase hexadecimal characters |
| `size_bytes` | `BIGINT` | Greater than zero and no more than 20 MiB |
| `mime_type` | `TEXT` | `image/jpeg` or `image/png` |
| `width_px` | `INTEGER` | Positive decoded width |
| `height_px` | `INTEGER` | Positive decoded height |
| `status` | `TEXT` | `ready` in this synchronous slice |
| `created_at` | `TIMESTAMPTZ` | UTC creation time |

No foreign key is added inside the existing JSONB `artifact_ids` task column.
`TaskService` enforces the one-ready-Artifact invariant for new task creation.
Existing task rows remain unchanged and readable.

The migration uses the existing explicit, ordered migration mechanism and is
safe to run repeatedly. It does not create storage directories or scan files.

## 6. Local Storage Design

The storage root comes from `BRIDGEAI_ARTIFACT_STORAGE_ROOT`; the local
development default is `var/artifacts/`. The directory is ignored by Git.

Storage keys are generated exclusively from the backend Artifact ID and verified
extension, for example:

```text
ab/art_ab12cd34ef56.jpg
```

The upload pipeline performs these steps:

1. Generate an Artifact ID and a temporary file under the configured root.
2. Stream the request into the temporary file while calculating SHA-256 and
   enforcing the 20 MiB limit.
3. Confirm the file signature, reopen it with the image decoder, and obtain its
   true MIME type and dimensions.
4. Atomically move the verified file to its generated final storage key.
5. Insert the metadata record in PostgreSQL.
6. If the database insert fails, remove only the file created by this operation.

The local filesystem and PostgreSQL do not share a distributed transaction. A
hard process termination after the atomic move but before metadata insertion can
leave an unreferenced file. Automatic orphan reconciliation is a later storage
governance slice; normal handled failures still perform compensating cleanup.

The store resolves and verifies every key under its configured root, rejects
absolute or escaping paths, and refuses symbolic links. Original filenames do
not participate in path resolution.

## 7. API Contract

### 7.1 Upload an Artifact

`POST /api/v1/artifacts` accepts one multipart field named `file` and returns
HTTP 201 with:

```json
{
  "artifact_id": "art_ab12cd34ef56",
  "original_filename": "bridge-span.jpg",
  "size_bytes": 483120,
  "mime_type": "image/jpeg",
  "width_px": 1920,
  "height_px": 1080,
  "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "status": "ready",
  "content_url": "/api/v1/artifacts/art_ab12cd34ef56/content",
  "created_at": "2026-08-01T04:00:00Z"
}
```

The API never returns `storage_key` or an absolute path.

### 7.2 Read Metadata and Content

- `GET /api/v1/artifacts/{artifact_id}` returns safe metadata.
- `GET /api/v1/artifacts/{artifact_id}/content` returns the verified image with
  its stored MIME type, a SHA-256-derived ETag, inline disposition, and private
  cache headers.

The content route looks up the Artifact record first and never treats a route
parameter as a filesystem path.

### 7.3 Create and Execute Tasks

`POST /api/v1/tasks` requires exactly one Artifact ID and rejects a reference
that is absent or not ready. The Vue workbench obtains this ID from the upload
response rather than user input.

Legacy task rows and run history remain readable. Running a legacy task whose
string reference has no Artifact record produces a persisted failed Workflow
snapshot with `ARTIFACT_NOT_FOUND`; it does not fabricate metadata or silently
fall back to the constant demo Tool.

The compatibility route `POST /api/v1/tasks/runs` applies the same one-ready-
Artifact validation to every new request. Compatibility means preserving the
request shape and persistent execution path, not allowing new arbitrary string
references. Previously persisted legacy rows remain the only exception.

## 8. Upload Integrity Checks

The backend dependency set adds Pillow for image signature verification,
decoding, dimensions, grayscale conversion, and deterministic filters. No
OpenCV or model-runtime dependency is introduced for this slice.

Upload-time checks establish whether bytes are safe and usable as an image:

- maximum request content of 20 MiB;
- accepted decoded formats limited to JPEG and PNG;
- agreement between decoded format and the verified MIME type;
- successful full image verification and reopen;
- positive decoded dimensions;
- valid SHA-256 and byte count.

Client-provided content type and filename extension are hints only. Animated
formats, SVG, HEIC, TIFF, video, archives, and files that merely use an image
extension are rejected. Image-decoder decompression-bomb protections remain
enabled.

Upload success means only that the Artifact is intact and ready for analysis;
it does not mean that its technical quality passed.

## 9. Technical Quality Analysis

The analyzer converts the image to grayscale for deterministic metrics. All
metrics and thresholds are finite JSON numbers.

| Check | Metric and default classification |
|---|---|
| Resolution | `fail` when the shorter side is below 720 px or total pixels are below 1,000,000; otherwise `pass` |
| Exposure mean | `fail` below 20 or above 235; `warn` below 40 or above 215; otherwise `pass` |
| Dark clipping | Fraction of grayscale pixels at or below 10; `fail` at 0.80 or above, `warn` at 0.50 or above |
| Bright clipping | Fraction of grayscale pixels at or above 245; `fail` at 0.80 or above, `warn` at 0.50 or above |
| Sharpness | RMS difference between grayscale content and a radius-1 Gaussian-blurred copy; `fail` below 2, `warn` below 5 |

The overall `quality_status` is `fail` when any check fails, `warn` when no
check fails and at least one warns, and `pass` otherwise. Thresholds live in one
typed configuration object and are serialized into every Tool result so a past
decision remains explainable if defaults later change.

The Tool result contains:

- Artifact ID;
- `quality_status`;
- analyzer version;
- actual metrics;
- thresholds used;
- per-check status;
- concise Chinese reasons.

The analyzer does not detect cracks, spalling, corrosion, deformation, or other
engineering diseases. Those remain separate versioned Tools.

## 10. LangGraph Semantics

`data_check` becomes a real Artifact verification node. It verifies that:

- the Artifact metadata exists and is ready;
- the stored file exists under the configured root and is not a symbolic link;
- current byte size and SHA-256 match PostgreSQL;
- the image remains decodable.

The graph conditionally routes an unsuccessful data check to `failed` without
executing `image_quality_check`. Stable error codes include:

- `ARTIFACT_NOT_FOUND`;
- `ARTIFACT_CONTENT_MISSING`;
- `ARTIFACT_INTEGRITY_MISMATCH`;
- `INVALID_IMAGE_ARTIFACT`.

The error code is stored in the Workflow JSON snapshot and failed-node history;
the existing run error message remains a sanitized human-readable summary.

The quality Tool has two distinct result dimensions:

- `ToolResult.ok=false` means the Tool or its infrastructure failed, so the
  Workflow becomes `failed`.
- `ToolResult.ok=true` with `quality_status=fail` means the analysis completed
  and found an unsuitable image. The Workflow remains `completed` and exposes
  the failed quality verdict.

This distinction prevents valid negative findings from being misreported as
system outages. Checkpoint state contains only Artifact IDs, metadata summaries,
metrics, thresholds, statuses, error codes, and reasons.

## 11. Frontend Interaction

`ArtifactUploadField` is integrated into `TaskCreateForm`.

### 11.1 Creation Flow

1. The empty state accepts a click or drag-and-drop of one file.
2. Upload locks task creation and shows a validation-and-save state.
3. Success displays a controlled preview, original name, byte size, dimensions,
   MIME type, abbreviated checksum, readiness status, and read-only Artifact ID.
4. Task submission automatically includes the returned Artifact ID.
5. If task creation fails, the successful upload remains selected so retry does
   not upload the same bytes again.

The manual Artifact ID textarea is removed. After successful upload, the first
slice provides no in-place replacement or delete action. Clearing the form and
uploading another image creates another Artifact; automatic cleanup of old
unbound uploads is deferred.

### 11.2 Run Detail

The history detail uses a reusable Artifact preview and adds a quality card:

- overall `质量通过`, `需要注意`, or `质量不合格` badge;
- resolution, exposure, clipping, and sharpness rows;
- actual metrics and thresholds;
- analyzer version and Chinese reasons;
- expandable raw Tool JSON for audit use.

Legacy history without a real Artifact displays `历史任务未关联真实图片` and
does not render a broken image or throw a frontend error.

## 12. Error Contract and Cleanup

| Condition | Result | Safe user message |
|---|---|---|
| Unsupported decoded type | HTTP 415 `UNSUPPORTED_ARTIFACT_TYPE` | 仅支持 JPEG、PNG |
| More than 20 MiB | HTTP 413 `ARTIFACT_TOO_LARGE` | 图片不得超过 20 MiB |
| Bad signature or decode | HTTP 422 `INVALID_IMAGE_ARTIFACT` | 文件不是有效图片或已损坏 |
| Local storage unavailable | HTTP 503 `ARTIFACT_STORAGE_UNAVAILABLE` | 检查 Artifact 存储目录 |
| Metadata database unavailable | HTTP 503 `DATABASE_UNAVAILABLE` | 图片未入库，可安全重试 |
| Task references a missing/non-ready Artifact | HTTP 422 `ARTIFACT_NOT_READY` | 请先上传有效图片 |
| Stored file missing or modified at execution | Persisted failed run snapshot | 图片文件缺失或完整性不一致 |

Known upload failures remove temporary files. A database failure after final
file creation removes only that operation's generated path. Errors and logs may
contain Artifact IDs and stable codes, but never absolute paths, credentials,
database connection strings, or raw stack traces in API responses.

## 13. Testing Strategy

Implementation follows test-first development with focused red-green cycles.

### 13.1 Python Unit Tests

- `LocalArtifactStore`: atomic writes, generated keys, root containment,
  traversal rejection, symlink rejection, missing content, and cleanup.
- `ArtifactService`: valid JPEG/PNG, false client MIME, corrupt files, oversized
  streams, decoder failures, and repository failure compensation.
- `ImageQualityAnalyzer`: normal, low-resolution, underexposed, overexposed,
  clipped, blurred, and exact boundary fixtures.
- LangGraph: verified Artifact success, missing/tampered Artifact failure,
  Tool infrastructure failure, and completed low-quality result.

Tests use generated or repository-owned non-sensitive image fixtures and real
code paths. Binary image data never enters checkpoint assertions.

### 13.2 PostgreSQL and API Tests

- ordered and repeatable migration application;
- Artifact create/read mapping in guarded `bridgeai_agent_test`;
- multipart upload and metadata response;
- controlled content response, MIME, ETag, and cache headers;
- every stable error response;
- task creation rejects zero, multiple, absent, or non-ready Artifacts;
- run history persists Artifact-driven Workflow and Tool snapshots.

### 13.3 Frontend Tests

- idle, uploading, success, and failure states;
- preview and metadata rendering;
- automatic task binding without a manual Artifact field;
- retrying task creation without a duplicate upload;
- quality badges, metrics, reasons, and raw audit detail;
- legacy task and run compatibility.

### 13.4 End-to-End Acceptance

1. Upload a normal JPEG or PNG and see its real preview and metadata.
2. Create a task with the automatically bound Artifact.
3. Execute it and see real quality metrics rather than a constant `pass`.
4. Refresh the browser and restart the backend; task, run, preview, and result
   remain available.
5. Upload a low-quality image and confirm a completed Workflow with a `warn` or
   `fail` quality verdict.
6. Tamper with a file only inside the dedicated test storage root and confirm a
   persisted failed run with an integrity error.
7. When health reports `model_gateway=configured`, complete one live oMLX run.
   Automated tests do not depend on the external gateway.

Fresh completion evidence requires:

```bash
BRIDGEAI_TEST_DATABASE_URL=... ./.venv/bin/python -m pytest -q
npm test --prefix frontend
npm run build --prefix frontend
./.venv/bin/python -m pip check
git diff --check
```

## 14. Explicitly Deferred Work

- MinIO or another S3-compatible ArtifactStore;
- multiple images per task and graph fan-out/fan-in;
- video, point cloud, TIFF, HEIC, SVG, or animated-image ingestion;
- Artifact replacement, delete, independent library, quotas, and orphan cleanup;
- thumbnail or derived-image generation;
- image enhancement and repair;
- bridge disease detection, segmentation, measurement, or classification;
- async upload, background workers, streaming progress, and cancellation;
- authentication, authorization, tenant isolation, and signed download URLs.

These boundaries keep the slice independently testable while establishing the
storage, API, Tool, Workflow, persistence, and UI seams required for later V0.3
Artifact and professional-tool work.
