# BridgeAI-Agent 第六章《RAG 行业知识库设计》编制设计

## 1. 编制目标

在现有前五章的架构约束下，编制第六章《RAG 行业知识库设计》V1.0，形成可指导 BridgeAI-Agent 第一阶段研发和验收的正式工程设计文档。

本章聚焦桥梁与道路巡检，不纳入智慧工地主线。内容既说明设计原则，也提供足够的数据契约、调用协议、治理规则、评测指标和实施范围，但不替代后续章节的详细设计。

## 2. 既有架构约束

第六章必须与前五章保持以下一致性：

- Agent 负责理解、规划和受策略约束的决策，Tool 负责专业能力执行。
- Workflow Runtime 以 LangGraph 为第一阶段核心编排运行时。
- RAG 负责可引用的外部工程依据；Memory 负责项目、任务及跨步骤上下文。
- RAG 能力通过符合 Tool SDK 的 RAG Tool 接入，不在 Agent 内部直接实现检索。
- PostgreSQL 保存权威业务元数据、版本、权限和审计记录。
- 原始文件及大体积解析产物进入 MinIO 或受控对象存储，不进入 Workflow State。
- 正式工程判断、处治决策及报告签发必须保留人工复核。
- 系统坚持本地优先、证据优先、模块可替换、权限隔离和全链路可追溯。

## 3. 职责边界

### 3.1 本章负责

- 行业知识分类与来源治理；
- 知识采集、解析、切分、索引和发布流程；
- PostgreSQL、Qdrant 与 MinIO 的职责划分；
- 关键词与向量混合检索、重排和上下文组织；
- 引用、证据链、冲突处理及拒答机制；
- RAG Tool 的输入输出和错误语义；
- RAG 与 Agent、Workflow、报告生成的集成边界；
- 知识版本、权限、安全、审计、可观测和评测；
- 第一阶段实现范围与架构决策。

### 3.2 本章不负责

- 项目记忆、任务记忆和用户偏好等 Memory 详细设计，由第七章负责；
- 完整 PostgreSQL 表结构、索引和迁移脚本，由第八章负责；
- 通用 Prompt 模板和结构化输出规范，由第十章负责；
- 前后端知识管理页面和接口细节，由第十一章负责；
- 全平台模型评测和生命周期管理，由第十二章负责；
- 生产部署、监控和安全基线的完整方案，由第十三章负责。

## 4. 目标应用场景

第一阶段围绕五类桥梁与道路巡检场景设计：

1. 病害术语、成因、影响和检查要点解释；
2. 标准、规范、指南及项目技术要求的条款检索；
3. 基于有效依据生成处治建议草案，并标注人工复核要求；
4. 历史病害、相似案例及既往处治效果检索；
5. 为巡检报告生成可追溯的引用和证据包。

## 5. 总体架构

```text
规范／标准／项目资料／历史案例／设备与模型文档
                         ↓
解析、OCR、表格抽取、结构识别
                         ↓
元数据补全、分块、质量检查、版本发布
                         ↓
PostgreSQL 元数据 + Qdrant 向量索引 + MinIO 原始文件
                         ↓
权限过滤 + 关键词／向量混合检索 + 重排
                         ↓
证据包组织 + 受约束生成 + 引用校验
                         ↓
RAG Tool → Agent／Workflow → 人工复核
```

### 5.1 存储职责

- PostgreSQL：知识源、文档、版本、适用范围、权限、发布状态、处理任务、引用和审计记录的权威数据源。
- Qdrant：向量及可过滤载荷索引，用于语义召回和混合检索。
- MinIO：原始文件、OCR 结果、版面分析结果及其他大体积 Artifact。
- Workflow State：只保存知识检索结果标识、引用标识和必要摘要，不保存完整文档或大体积证据内容。

### 5.2 检索链路

1. 识别查询意图、资产类型、病害类型、时间和适用范围；
2. 执行用户、组织、项目和知识域权限过滤；
3. 并行执行关键词检索与向量检索；
4. 合并、去重并重排候选片段；
5. 检查版本有效性、来源可信度、适用性和证据覆盖；
6. 组织带引用的 Evidence Pack；
7. 在受约束生成后校验引用与原文支持关系；
8. 将结果、版本、耗时和审计信息返回 RAG Tool 调用方。

## 6. 知识治理要求

- 知识源至少分为法规与标准、设计与检测规范、项目资料、历史案例、病害知识、设备与模型文档。
- 规范类文档必须记录编号、名称、版本、发布机构、发布日期、实施日期、失效状态和适用范围。
- 文档入库与知识发布分离；未通过解析质量、元数据完整性和权限检查的版本不得进入生产检索。
- 知识版本发布后不可原地覆盖；更新通过新版本、有效期和替代关系表达。
- 来源冲突时保留冲突证据，不以生成模型自动裁决工程责任问题。
- 删除向量索引或文件 Artifact 时，必须与权威元数据状态及审计记录一致。

## 7. 证据与安全约束

- 每个事实性或规范性结论必须绑定来源文档、版本、页码、章节或条款定位。
- 证据不足、来源冲突、规范过期或适用性不明确时，系统应降级为提示、追问或人工复核，不输出确定性结论。
- 检索前必须执行访问控制；生成后不得泄漏调用者无权访问的来源标题、摘要或片段。
- 外部文档内容按不可信输入处理，防范提示注入和恶意指令进入系统 Prompt 或 Tool 控制面。
- 正式评定、处治决策、设备控制和报告签发不得由 RAG 结果直接触发。

## 9. 技术深度控制

正文应包含：

- 必要的架构图、处理流程图和时序说明；
- 关键 Pydantic 输入输出示例；
- 核心元数据和 Evidence Pack 字段示例；

## 10. 验收标准

第六章完成后应满足：

1. 标题、编号、术语、文档信息表和修订记录与第三至第五章风格一致；
2. 不改变前五章已确定的 Agent、Workflow、Tool 和数据边界；
3. 清晰区分 RAG、Memory、业务数据和 Workflow State；
4. 能指导第一阶段 RAG Tool、知识入库和检索链路的实现；
5. 同时定义检索召回、引用准确性、答案忠实度、权限隔离、版本正确性和性能指标；
6. 所有时效性技术事实和标准信息使用当前官方资料核验，并提供可读参考链接；
7. 不含 TBD、TODO、占位文字或无法执行的模糊要求；
8. Markdown 标题层级、代码围栏、表格及内部引用通过一致性检查。
