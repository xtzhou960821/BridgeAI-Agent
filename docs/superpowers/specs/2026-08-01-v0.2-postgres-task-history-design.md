# V0.2 PostgreSQL Task History Design

## Goal

Close the existing V0.2 oMLX Model Gateway integration as a verified commit, then add a PostgreSQL-backed task workflow that lets users create inspection tasks, execute each task multiple times, and recover execution history after page or service restarts.

## Scope and Delivery Order

The work is delivered in two independent commits.

### Commit 1: Close the existing V0.2 Model Gateway integration

- Preserve the current oMLX `DeepSeek-V4-Flash-4bit` task-understanding integration.
- Fix the duplicate task-list heading in the Vue template.
- Verify the Python suite, frontend production build, backend/frontend startup, health refresh, and one live example task execution.
- Update the README and V0.2 local runbook so their commands and feature descriptions match the verified system.
- Do not include PostgreSQL task-history behavior in this commit.

### Commit 2: Add persistent task creation and execution history

- Replace the frontend's hard-coded example task with tasks loaded from the backend.
- Persist task definitions and every execution in PostgreSQL.
- Restore the task list and run history after browser refresh and backend restart.
- Keep task execution synchronous in V0.2; queues, workers, SSE, and WebSockets remain out of scope.

The second commit does not add organizations, projects, authentication, RLS, Artifact object storage, full Workflow event tables, background workers, or the production `bridgeai_workflow` schema. Its boundaries must allow those capabilities to replace or extend the V0.2 implementation later.

## Architecture

The backend keeps protocol adaptation, orchestration, and persistence separate:

```text
Vue workbench
  -> FastAPI task routes
  -> task application service
  -> PostgreSQL task repository
  -> inspection_tasks / inspection_task_runs

Task execution service
  -> AgentRunner
  -> Model Gateway
  -> Tool SDK
  -> PostgreSQL run snapshot update
```

FastAPI routes validate requests and translate known failures into stable HTTP errors. The application service owns create, list, execute, and history use cases. The repository owns SQL and transaction boundaries. Agent and Tool modules do not import database code.

PostgreSQL is the sole persisted business-state implementation. No in-memory, SQLite, or JSON-file persistence fallback is introduced.

## PostgreSQL Model

### `inspection_tasks`

The existing V0.2 table is extended rather than dropped or replaced.

| Column | Purpose |
|---|---|
| `task_id` | Backend-generated stable task identifier and primary key |
| `title` | User-facing task name |
| `task_type` | V0.2 task type, initially `bridge_inspection` |
| `objective` | Task-understanding objective |
| `artifact_ids` | JSONB array of Artifact identifiers |
| `status` | Current business status: `draft`, `running`, `completed`, or `failed` |
| `idempotency_key` | Optional unique create-request key |
| `created_at` | Creation timestamp |
| `updated_at` | Last state-change timestamp |

The migration validates that `artifact_ids` is a JSON array and that required text fields are nonblank. Existing rows receive safe V0.2 defaults during migration.

### `inspection_task_runs`

Each execution is an independent immutable-identity row whose status and result fields are updated as the run progresses.

| Column | Purpose |
|---|---|
| `run_id` | Backend-generated stable run identifier and primary key |
| `task_id` | Foreign key to `inspection_tasks` |
| `run_number` | Per-task monotonically increasing execution number |
| `status` | `running`, `completed`, or `failed` |
| `agent_model` | JSONB snapshot of the model profile |
| `workflow` | JSONB snapshot of Workflow state and step outputs |
| `tool_results` | JSONB array of Tool result snapshots |
| `error_message` | Sanitized failure summary when failed |
| `started_at` | Run start timestamp |
| `completed_at` | Terminal timestamp for completed or failed runs |

`(task_id, run_number)` is unique. Creating a run locks the task row inside the transaction before allocating the next run number. Indexes support recent task listing and reverse-chronological run history.

### Migrations

A small explicit migration command uses `psycopg 3`, scans ordered SQL files, and records applied filenames in a migration table. Every migration runs transactionally and is recorded only after success. The command is safe to invoke repeatedly. Backend startup checks configuration and connectivity but never mutates the schema automatically.

## API Contract

### Create a task

`POST /api/v1/tasks`

Request body:

```json
{
  "title": "桥梁无人机影像质量检查",
  "task_type": "bridge_inspection",
  "objective": "检查桥梁无人机影像质量",
  "artifact_ids": ["art_001"]
}
```

The client may provide `Idempotency-Key`. Repeating an identical request with the same key returns the existing task. Reusing the key with different content returns `409 IDEMPOTENCY_CONFLICT`.

### Query tasks and history

- `GET /api/v1/tasks` returns tasks by most recent update time.
- `GET /api/v1/tasks/{task_id}` returns one task.
- `GET /api/v1/tasks/{task_id}/runs` returns that task's runs by descending run number.

The V0.2 list response is bounded to the newest 50 records. Cursor pagination is deferred until the data volume justifies it.

Task responses expose `task_id`, `title`, `task_type`, `objective`, `artifact_ids`, `status`, `created_at`, and `updated_at`. Run responses expose `run_id`, `task_id`, `run_number`, `status`, the three result snapshots, `error_message`, `started_at`, and `completed_at`. Timestamps use UTC ISO 8601 strings.

### Execute a task

`POST /api/v1/tasks/{task_id}/runs`

The service loads the saved task input, creates a `running` run, updates the task to `running`, calls the existing Agent Runner, and then atomically writes either the completed snapshots or a failed error summary. The response contains the persisted run representation.

The existing `POST /api/v1/tasks/runs` endpoint remains as a compatibility adapter for the current sample request. It creates the named task when absent, validates that an existing task with that identifier has the same execution input, and delegates execution to the same persistent service so it cannot bypass PostgreSQL history. Conflicting existing input returns `409 TASK_INPUT_CONFLICT`.

## Frontend Interaction

The workbench contains four coordinated areas:

1. Service and model status.
2. A task-creation form with title, objective, task type, and Artifact identifiers.
3. A persisted task list with the selected task and its current status.
4. A run-history list and selected-run detail showing the model result, Workflow timeline, and Tool outputs.

On mount, the page loads health and tasks in parallel. It selects the most recently updated task, then loads that task's run history. Creating a task selects the new record. Running a task refreshes both the task and its history. Selecting another task or run updates the detail without rerunning anything.

Create, run, task-load, and history-load operations have separate busy, empty, and error states. Buttons are disabled only for the operation they initiate. The existing monolithic `App.vue` is split into typed API helpers and focused form, list, history, and result components; `App.vue` remains the page-level coordinator.

## Error Handling

| Condition | API behavior | Persisted behavior |
|---|---|---|
| Database URL missing | `503 DATABASE_UNAVAILABLE` | No write attempted |
| Database unreachable or schema missing | `503 DATABASE_UNAVAILABLE` | No partial task/run write |
| Task missing | `404 TASK_NOT_FOUND` | No run created |
| Idempotency key conflicts | `409 IDEMPOTENCY_CONFLICT` | Existing task unchanged |
| Model profile/key missing | `503 MODEL_GATEWAY_NOT_CONFIGURED` | Run is marked `failed` if it was already created |
| Model or Tool execution fails | Stable execution error response | Run becomes `failed` with terminal time and sanitized message; task becomes `failed` |

Health distinguishes `database=not_configured`, `database=unavailable`, and `database=ready`. Error payloads contain a stable code and user-readable message; secrets, connection strings, and raw model credentials are never returned.

## Testing and Acceptance

### Model Gateway closeout gate

- Full Python test suite passes.
- `npm run build` passes.
- Backend and frontend start from documented commands.
- Browser verifies health refresh and one live oMLX task execution.
- README and V0.2 runbook match the tested workflow.
- `git diff --check` passes before the closeout commit.

### PostgreSQL task-history gate

- Migration tests prove ordered application and repeatability.
- Repository tests use a dedicated test database or isolated test schema and cover create, idempotent create, list, detail, run allocation, completion, failure, and history ordering.
- Service and API tests cover success and all documented errors.
- The full Python suite and frontend production build pass.
- Browser verification completes: create a task, run it twice, switch between run details, refresh the page, restart the backend, and confirm both runs remain available.
- Tests and cleanup target only the dedicated test database/schema; existing user databases and tables are never broadly deleted.
- `git diff --check` passes before the feature commit.

## Deferred Work

- Organization/project scope, authentication, authorization, and RLS.
- Full `bridgeai_workflow.workflow_tasks`, `workflow_runs`, event, node-execution, and review schema.
- Artifact upload and object storage.
- Asynchronous workers, cancellation, retry, SSE, and WebSocket progress.
- Pagination beyond the bounded V0.2 list.

These are deferred deliberately; the Repository and service boundaries are the migration seam for later versions.
