# V0.2 PostgreSQL Task History Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the existing V0.2 oMLX integration, then let users create inspection tasks and recover every execution from PostgreSQL after browser or service restarts.

**Architecture:** FastAPI routes adapt HTTP requests into a task application service. The service coordinates the existing Agent Runner and a synchronous PostgreSQL repository; task identity and run metadata stay relational while model, Workflow, and Tool outputs are stored as JSONB snapshots. Vue loads persisted tasks and histories through typed API helpers and focused components.

**Tech Stack:** Python 3.12, FastAPI, psycopg 3, PostgreSQL 17, pytest, Vue 3, TypeScript, Vite, Vitest, Vue Test Utils, Chrome browser verification.

## Global Constraints

- Deliver source work in two code commits: the Model Gateway closeout first, then the complete PostgreSQL task-history feature.
- PostgreSQL is the only business-state persistence implementation; do not add in-memory, SQLite, or JSON-file fallbacks.
- Keep execution synchronous in V0.2; do not add queues, workers, SSE, WebSockets, cancellation, or retries.
- Keep organizations, projects, authentication, RLS, Artifact object storage, and the production `bridgeai_workflow` schema out of this slice.
- Never print, commit, or return `BRIDGEAI_AGENT_API_KEY` or a database password.
- Run destructive test setup only against the exact database name `bridgeai_agent_test`.
- Use TDD for new Python and Vue behavior: observe each focused test fail before production implementation.
- Preserve `POST /api/v1/tasks/runs`, but route it through PostgreSQL persistence.
- Backend startup may check database readiness but must never apply migrations automatically.

```python
def get_database_url(environ=None) -> str:
    source = os.environ if environ is None else environ
    return source.get("BRIDGEAI_DATABASE_URL", "").strip()


def connect(database_url: str):
    return psycopg.connect(database_url)


def probe_database(database_url: str) -> bool:
    if not database_url:
        return False
    try:
        with connect(database_url) as connection:
            tables = connection.execute(
                "SELECT to_regclass('public.inspection_tasks'), "
                "to_regclass('public.inspection_task_runs')",
            ).fetchone()
        return bool(tables and all(tables))
    except psycopg.Error:
        return False
```

- [ ] **Step 6: Implement the migration runner**

Create `migrate.py` around this exact transaction loop:

```python
MIGRATIONS_DIR = Path(__file__).with_name("migrations")


def apply_migrations(database_url: str, migrations_dir: Path | None = None) -> list[str]:
    directory = MIGRATIONS_DIR if migrations_dir is None else migrations_dir
    applied_now: list[str] = []
    with connect(database_url) as connection:
        connection.execute(
            "CREATE TABLE IF NOT EXISTS bridgeai_schema_migrations ("
            "filename TEXT PRIMARY KEY, applied_at TIMESTAMPTZ NOT NULL DEFAULT NOW())",
        )
        applied = {
            row[0]
            for row in connection.execute(
                "SELECT filename FROM bridgeai_schema_migrations",
            ).fetchall()
        }
        for path in sorted(directory.glob("*.sql")):
            if path.name in applied:
                continue
            connection.execute(path.read_text(encoding="utf-8"))
            connection.execute(
                "INSERT INTO bridgeai_schema_migrations (filename) VALUES (%s)",
                (path.name,),
            )
            applied_now.append(path.name)
    return applied_now
```

Add `main()` that requires `get_database_url()` and prints only `applied <filename>` lines. The connection context makes the batch transactional.
