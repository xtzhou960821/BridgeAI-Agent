# BridgeAI-Agent V0.2 本地运行说明

本说明对应 V0.2 本地联调版本及第一段 V0.3 Artifact/图像质量切片，目标是验证 oMLX Model Gateway、PostgreSQL 任务持久化、本地 Artifact 字节存储和 Vue 工作台的完整闭环，而不是启动生产系统。该切片不代表 V0.3 的全部 Tool 已完成。

## 已验证命令

```bash
set -a
source .env
set +a
export BRIDGEAI_TEST_DATABASE_URL="${BRIDGEAI_DATABASE_URL%/*}/bridgeai_agent_test"
export LANGGRAPH_STRICT_MSGPACK=true
./.venv/bin/python -m backend.app.repositories.postgres.migrate
./.venv/bin/python -m pytest -q
npm test --prefix frontend
npm run build --prefix frontend
./.venv/bin/python -m pip check
git diff --check
```

该命令会验证当前纯 Python 核心：

- Tool SDK 注册、必填输入校验、真实图像质量指标和执行结果；
- LangGraph 五节点状态推进、Artifact 完整性复核、Tool 条件路由和 checkpoint 安全序列化；
- Agent Runner 最小任务循环；
- PostgreSQL 业务迁移、Artifact 元数据、LangGraph Checkpointer setup、任务仓储、执行成功与失败历史；
- FastAPI Artifact 上传/读取、持久化任务接口、运行时元数据与实时数据库健康状态；
- Vue 图片上传、任务创建、持久化预览、质量卡片、历史切换与 LangGraph runtime/thread 展示；
- Python 与前端依赖一致性、生产构建和空白字符检查。

`BRIDGEAI_TEST_DATABASE_URL` 必须明确指向 `bridgeai_agent_test`。测试准备会清理该测试库中的 V0.2 任务表，因此保护逻辑会拒绝任何其他数据库名。

## PostgreSQL 准备与迁移

本机需要存在开发数据库与隔离测试数据库。可先只读检查：

```bash
psql -d postgres -Atc "SELECT datname FROM pg_database WHERE datname IN ('bridgeai', 'bridgeai_agent_test') ORDER BY datname"
```

若某个数据库不存在，再单独创建缺失项；不要删除或重建已有数据库：

```bash
createdb -O bridgeai bridgeai
createdb -O bridgeai bridgeai_agent_test
```

开发连接通过本地 `.env` 的 `BRIDGEAI_DATABASE_URL` 提供。先安装依赖并检查依赖一致性：

```bash
./.venv/bin/python -m pip install -e ".[backend,dev]"
./.venv/bin/python -m pip check
```

然后分别执行 BridgeAI 业务迁移与官方 LangGraph Checkpointer setup：

```bash
set -a
source .env
set +a
export LANGGRAPH_STRICT_MSGPACK=true
export BRIDGEAI_ARTIFACT_STORAGE_ROOT="${BRIDGEAI_ARTIFACT_STORAGE_ROOT:-var/artifacts}"
./.venv/bin/python -m backend.app.repositories.postgres.migrate
./.venv/bin/python -m backend.app.repositories.postgres.checkpoints
```

业务迁移记录在 `bridgeai_schema_migrations`。命令可以重复执行，已应用文件不会再次运行；后端启动只检查表是否就绪，不会自动迁移。`0003_langgraph_runtime.sql` 为 `inspection_task_runs` 增加 `workflow_runtime` 和 `checkpoint_thread_id`，并约束每个 LangGraph 业务运行绑定唯一且非空的 checkpoint thread。

Checkpointer setup 是独立命令，由 `langgraph-checkpoint-postgres` 官方 `PostgresSaver.setup()` 创建或升级 `checkpoint_migrations`、`checkpoints`、`checkpoint_blobs` 和 `checkpoint_writes`。该命令可重复执行；建议连续执行两次验证幂等性。业务迁移不会创建这些框架表，Checkpointer setup 也不会替代业务迁移。

`LANGGRAPH_STRICT_MSGPACK=true` 要在测试、setup 和后端运行时保持一致，用于启用 PostgreSQL Checkpointer 推荐的严格 msgpack 反序列化，并将可反序列化类型限制在安全白名单内。与此独立，BridgeAI 自身的状态规范化边界会在图状态进入 checkpoint 前仅保留 serializer-safe 值，并拒绝不支持的运行时对象。Artifact checkpoint 只包含允许的元数据，不包含图片字节、绝对路径、密钥或数据库连接串。

## Artifact 存储准备

`BRIDGEAI_ARTIFACT_STORAGE_ROOT` 指定原始图片字节的本地存储根目录；未设置时使用仓库内的 `var/artifacts`。启动后端的系统用户必须能创建和读写该目录。PostgreSQL 的 `inspection_artifacts` 只保存 Artifact ID、相对 storage key、SHA-256、大小、MIME、尺寸、状态和时间；图片字节不会写入数据库。

```bash
export BRIDGEAI_ARTIFACT_STORAGE_ROOT="${BRIDGEAI_ARTIFACT_STORAGE_ROOT:-var/artifacts}"
mkdir -p "$BRIDGEAI_ARTIFACT_STORAGE_ROOT"
```

上传会以 1 MiB 分块暂存并在超过 20 MiB 时停止，随后以 Pillow 完整解码内容；只接收单帧 JPEG 或 PNG，并拒绝动画、多帧和触发解压炸弹保护的图片。客户端文件名与声明的 Content-Type 都不决定最终格式和存储路径，原始文件名不能把字节写出存储根目录。

## 后端启动

完成迁移后启动后端：

```bash
set -a
source .env
set +a
export LANGGRAPH_STRICT_MSGPACK=true
./.venv/bin/python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

也可以直接让 Uvicorn 读取本地环境文件：

```bash
LANGGRAPH_STRICT_MSGPACK=true ./.venv/bin/python -m uvicorn backend.app.main:app --env-file .env --host 127.0.0.1 --port 8000
```

健康检查路径：

```text
GET /api/v1/health
```

健康组件含义：

- `database=ready`：业务数据库可连接；`unavailable` 表示连接失败，`not_configured` 表示没有连接配置。
- `langgraph_checkpointer=ready`：四张官方 checkpoint 表都存在且可探测。
- `langgraph_checkpointer=not_initialized`：数据库可连接，但 checkpoint 表尚未 setup；先执行 `./.venv/bin/python -m backend.app.repositories.postgres.checkpoints`。
- `langgraph_checkpointer=unavailable`：无法探测 checkpoint 存储；检查 `BRIDGEAI_DATABASE_URL`、PostgreSQL 进程、网络、权限和数据库名，修复后重新执行 setup。

任务执行返回 HTTP 503 和 `LANGGRAPH_CHECKPOINTER_NOT_READY` 时，不会降级到内存 checkpointer。确认健康状态，重新执行显式 Checkpointer setup，再重试新运行；不要通过启动参数绕过持久化要求。

持久化 API：

```text
POST /api/v1/artifacts
GET  /api/v1/artifacts/{artifact_id}
GET  /api/v1/artifacts/{artifact_id}/content
POST /api/v1/tasks
GET  /api/v1/tasks
GET  /api/v1/tasks/{task_id}
POST /api/v1/tasks/{task_id}/runs
GET  /api/v1/tasks/{task_id}/runs
POST /api/v1/tasks/runs               # V0.2 兼容入口，同样写入 PostgreSQL
```

### 上传、创建、执行和读取

先上传一张本机真实图片。响应为 HTTP 201，并包含后续请求必须使用的 `artifact_id`、`sha256`、`size_bytes`、`mime_type`、`width_px`、`height_px`、`status=ready` 和相对 API `content_url`：

```bash
curl -sS -X POST http://127.0.0.1:8000/api/v1/artifacts \
  -F "file=@/absolute/path/to/bridge-image.jpg"
```

将响应中的 ID 写入 shell 变量（以下值只是占位，必须替换为刚才上传返回的 `art_...`）：

```bash
ARTIFACT_ID="art_replace_with_uploaded_id"
```

每个新任务必须且只能关联一个已上传、`ready` 的 Artifact。建议为创建请求设置新的幂等键；同一键和同一内容可安全重试，不同内容会返回 `409 IDEMPOTENCY_CONFLICT`：

```bash
curl -sS -X POST http://127.0.0.1:8000/api/v1/tasks \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: create-local-001" \
  -d '{
    "title": "桥梁无人机影像质量检查",
    "task_type": "bridge_inspection",
    "objective": "检查桥梁无人机影像质量",
    "artifact_ids": ["'"$ARTIFACT_ID"'"]
  }'

TASK_ID="task_replace_with_created_id"
curl -sS -X POST "http://127.0.0.1:8000/api/v1/tasks/$TASK_ID/runs"
curl -sS "http://127.0.0.1:8000/api/v1/tasks/$TASK_ID/runs"

curl -sS "http://127.0.0.1:8000/api/v1/artifacts/$ARTIFACT_ID"
curl -sS "http://127.0.0.1:8000/api/v1/artifacts/$ARTIFACT_ID/content" \
  --output /tmp/bridgeai-artifact-preview.jpg
```

内容读取会先重新核对文件存在性、字节数、SHA-256、解码格式和尺寸；成功响应附带 SHA-256 ETag 并以内联 JPEG/PNG 返回。不要用样例文件中的 Artifact ID 直接调用接口，它不是内置对象。

### 图像质量结果语义

`image_quality_check` 当前分析器版本为 `0.1.0`。Tool 输出包括：

- `quality_status`：`pass`、`warn` 或 `fail`；
- `metrics`：短边、总像素、平均亮度、暗/亮裁剪比例和清晰度 RMS；
- `thresholds`：该分析器版本实际使用的分辨率、曝光、裁剪和清晰度阈值；
- `checks`：逐项 `pass`/`warn`/`fail`；
- `reasons`：所有未通过项的稳定中文原因；
- `analyzer_version`：解释指标时必须一同保存的版本。

质量 `warn` 或 `fail` 是一次成功完成的负面检测结论，任务运行仍为 `completed`。只有 Tool 无法执行、Artifact 完整性错误或其他执行错误才令 Workflow 为 `failed`。因此调用方不能用 HTTP 成功或任务 `completed` 代替读取 `quality_status`。

### 限制与稳定修复指引

- `413 ARTIFACT_TOO_LARGE`：图片超过 20 MiB；在客户端压缩/缩放后重新上传，不要修改已保存 Artifact。
- `415 UNSUPPORTED_ARTIFACT_TYPE`：完整解码后的格式不是 JPEG/PNG，或图片包含动画/多帧；转换为单帧 JPEG/PNG 后重新上传，改扩展名或伪造 Content-Type 无效。
- `422 INVALID_IMAGE_ARTIFACT`：字节不是可完整解码的图片、已经损坏，或触发 Pillow 解压炸弹保护；从可信源安全缩放或重新导出后上传，不要关闭解码保护。
- `422 ARTIFACT_NOT_READY`：新任务没有且仅有一个真实 ready Artifact；先调用上传接口并使用返回 ID。
- `410 ARTIFACT_CONTENT_MISSING`：内容读取接口发现数据库元数据存在但本地字节缺失；任务执行则把同一码写入失败 Workflow。恢复与该元数据 SHA-256/大小/格式/尺寸完全一致的备份，或重新上传并创建新任务。
- `409 ARTIFACT_INTEGRITY_MISMATCH`：内容读取接口发现本地字节与不可变元数据不一致；任务执行则把同一码写入失败 Workflow。停止使用该 Artifact，从可信备份恢复完全相同字节，或重新上传原始文件并创建引用新 ID 的任务。不要改数据库摘要来掩盖错误。
- `503 ARTIFACT_STORAGE_UNAVAILABLE`：确认 `BRIDGEAI_ARTIFACT_STORAGE_ROOT` 指向预期目录且后端用户有权限，然后以同一环境重启后端。

历史 string-only Artifact 引用及其任务/运行记录仍可读取，工作台会显示“历史任务未关联真实图片”。系统不会为旧字符串伪造 Artifact 元数据或图片内容；重新执行这类任务会以明确的 Artifact 缺失错误结束。若要恢复可执行状态，应上传真实图片并创建引用新 ID 的任务，不要篡改旧历史。

建议使用 `python -m uvicorn`，这样可以确保调用的是当前虚拟环境中的 Uvicorn，而不是 Anaconda 或系统环境中的全局命令。

## 前端启动

安装前端依赖并启动：

```bash
npm install --prefix frontend
npm run dev --prefix frontend -- --host 127.0.0.1 --port 5173
```

工作台会先上传并预览 JPEG/PNG，自动将返回的 Artifact ID 放入创建请求，再从后端加载 PostgreSQL 任务和执行历史。每次执行都保存独立的模型 Profile、任务理解结果与 usage、Workflow 历史、真实质量 Tool 输出、失败信息、`workflow_runtime` 和 `checkpoint_thread_id`；刷新浏览器或重启后端不会丢失数据库记录和本地 Artifact 预览。

## 业务历史与框架 checkpoint 的所有权

BridgeAI 业务表 `inspection_tasks` 和 `inspection_task_runs` 是面向 API 与工作台的历史来源，保存任务、运行编号、最终状态和可展示的执行快照。每次业务运行都使用 `checkpoint_thread_id=run_id`，因此两次运行的图状态不会混入同一 thread。

LangGraph 官方表只保存图的 checkpoint、channel value 和 pending write 等框架状态。应用不把这些表当作业务历史 API，也不把业务 JSONB 快照当作 LangGraph 恢复协议。

当前运行链路不是跨两套表的原子事务：进程若在 LangGraph 已写 checkpoint、但业务运行最终快照尚未提交时崩溃，两侧可能短暂不一致。本切片不提供 resume/retry、崩溃对账或孤立 checkpoint 清理；interrupts、异步 workers、streaming、Store、Memory 和 RAG 也延后实现。发生这类故障时先保留业务运行和 checkpoint 证据，再由后续 reconciliation 机制处理，不要手工把单侧数据伪造成完成状态。

## V0.2 联调验收

启动前后端后执行以下两次运行验收：

1. 上传一张已知 JPEG/PNG，确认预览、大小、尺寸、MIME、SHA-256 前缀和 `ready`，再创建桥梁巡检任务；确认 Artifact ID 由上传结果自动填入。
2. 执行任务，确认 `quality_status`、真实 `metrics`、`thresholds`、`checks`、`reasons`、`analyzer_version`、模型 Profile/usage、`workflow_runtime=langgraph` 和 `checkpoint_thread_id=run_id`。
3. 连续执行第二次，确认两次 run ID/thread ID 不同，分别使用官方 `PostgresSaver.list()` 读取 checkpoint，且每个 thread 至少有五个 checkpoint。
4. 在工作台切换两次运行，模型、Workflow、Tool、runtime 和 thread 快照应随选择变化；Workflow 依次显示 `task_understanding`、`data_check`、`image_quality_check`、`completed`。
5. 刷新页面，再只停止并重启后端，确认任务、两条运行、Artifact 预览、质量结果和 thread 仍在，`langgraph_checkpointer=ready`。
6. 另上传一张已知低质量图片并运行，确认运行是 `completed`，而质量徽章为 `warn` 或 `fail`。最后检查浏览器控制台无 JavaScript 错误，并在 390 × 844 视口复核核心内容。

## 数据库迁移文件

迁移文件位于：

```text
backend/app/repositories/postgres/migrations/0001_v0_2_skeleton.sql
backend/app/repositories/postgres/migrations/0002_task_history.sql
backend/app/repositories/postgres/migrations/0003_langgraph_runtime.sql
backend/app/repositories/postgres/migrations/0004_langgraph_thread_identity.sql
backend/app/repositories/postgres/migrations/0005_artifacts.sql
```

`0001` 创建最小任务表，`0002` 扩展任务字段并创建每次执行的历史表 `inspection_task_runs`，`0003` 增加 LangGraph runtime/thread 元数据、约束和唯一索引，`0004` 强制 LangGraph 运行使用 `checkpoint_thread_id=run_id`，`0005_artifacts.sql` 创建只保存已验证图片元数据的 `inspection_artifacts` 表及约束/索引。官方 checkpoint 表由独立 setup 命令管理，不属于这些业务 SQL 迁移。

## Agent Model Profile

当前默认 Agent Model Profile 为：

```text
model_id=DeepSeek-V4-Flash-4bit
model_version=omlx-current
alias=omlx-deepseek-v4-flash
provider=omlx
runtime=openai-compatible
api_base_url=https://omlx.cpolar.cn/v1
timeout_seconds=60
is_stub=false
```

任务理解阶段会通过 OpenAI-compatible Model Gateway 调用该模型，模型理解结果、模型 Profile 和 usage 会随 Workflow 返回。API key 使用本地 `.env` 的 `BRIDGEAI_AGENT_API_KEY`，不要写入仓库。
