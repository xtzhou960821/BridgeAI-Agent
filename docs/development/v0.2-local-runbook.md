# BridgeAI-Agent V0.2 本地运行说明

本说明对应 V0.2 本地联调版本，目标是验证 oMLX Model Gateway、PostgreSQL 任务持久化和 Vue 工作台的完整闭环，而不是启动生产系统。

## 已验证命令

```bash
set -a
source .env
set +a
export BRIDGEAI_TEST_DATABASE_URL="${BRIDGEAI_DATABASE_URL%/*}/bridgeai_agent_test"
export LANGGRAPH_STRICT_MSGPACK=true
./.venv/bin/python -m pytest -q
npm test --prefix frontend -- --run
npm run build --prefix frontend
./.venv/bin/python -m pip check
git diff --check
```

该命令会验证当前纯 Python 核心：

- Tool SDK 注册、必填输入校验和执行结果；
- LangGraph 五节点状态推进、Tool 条件路由和 checkpoint 序列化；
- Agent Runner 最小任务循环；
- PostgreSQL 业务迁移、LangGraph Checkpointer setup、任务仓储、执行成功与失败历史；
- FastAPI 持久化任务接口、运行时元数据与实时数据库健康状态；
- Vue API、任务创建、历史切换与 LangGraph runtime/thread 展示；
- Python 与前端依赖一致性、生产构建和空白字符检查。

`BRIDGEAI_TEST_DATABASE_URL` 必须明确指向 `bridgeai_agent_test`。测试准备会清理该测试库中的 V0.2 任务表，因此保护逻辑会拒绝任何其他数据库名。

## PostgreSQL 准备与迁移

本机需要存在开发数据库与隔离测试数据库。可先只读检查：

```bash
psql -d postgres -Atc "SELECT datname FROM pg_database WHERE datname IN ('bridgeai', 'bridgeai_agent_test') ORDER BY datname"
```

若某个数据库不存在，再单独创建缺失项；不要删除或重建已有数据库：

```bash
createdb -O bridgeai bridgeai
createdb -O bridgeai bridgeai_agent_test
```

开发连接通过本地 `.env` 的 `BRIDGEAI_DATABASE_URL` 提供。先安装依赖并检查依赖一致性：

```bash
./.venv/bin/python -m pip install -e ".[backend,dev]"
./.venv/bin/python -m pip check
```

然后分别执行 BridgeAI 业务迁移与官方 LangGraph Checkpointer setup：

```bash
set -a
source .env
set +a
export LANGGRAPH_STRICT_MSGPACK=true
./.venv/bin/python -m backend.app.repositories.postgres.migrate
./.venv/bin/python -m backend.app.repositories.postgres.checkpoints
```

业务迁移记录在 `bridgeai_schema_migrations`。命令可以重复执行，已应用文件不会再次运行；后端启动只检查表是否就绪，不会自动迁移。`0003_langgraph_runtime.sql` 为 `inspection_task_runs` 增加 `workflow_runtime` 和 `checkpoint_thread_id`，并约束每个 LangGraph 业务运行绑定唯一且非空的 checkpoint thread。

Checkpointer setup 是独立命令，由 `langgraph-checkpoint-postgres` 官方 `PostgresSaver.setup()` 创建或升级 `checkpoint_migrations`、`checkpoints`、`checkpoint_blobs` 和 `checkpoint_writes`。该命令可重复执行；建议连续执行两次验证幂等性。业务迁移不会创建这些框架表，Checkpointer setup 也不会替代业务迁移。

`LANGGRAPH_STRICT_MSGPACK=true` 要在测试、setup 和后端运行时保持一致，使 checkpoint 序列化严格拒绝不支持的值，避免运行后才暴露不可移植状态。

## 后端启动

完成迁移后启动后端：

```bash
set -a
source .env
set +a
export LANGGRAPH_STRICT_MSGPACK=true
./.venv/bin/python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

也可以直接让 Uvicorn 读取本地环境文件：

```bash
LANGGRAPH_STRICT_MSGPACK=true ./.venv/bin/python -m uvicorn backend.app.main:app --env-file .env --host 127.0.0.1 --port 8000
```

健康检查路径：

```text
GET /api/v1/health
```

健康组件含义：

- `database=ready`：业务数据库可连接；`unavailable` 表示连接失败，`not_configured` 表示没有连接配置。
- `langgraph_checkpointer=ready`：四张官方 checkpoint 表都存在且可探测。
- `langgraph_checkpointer=not_initialized`：数据库可连接，但 checkpoint 表尚未 setup；先执行 `./.venv/bin/python -m backend.app.repositories.postgres.checkpoints`。
- `langgraph_checkpointer=unavailable`：无法探测 checkpoint 存储；检查 `BRIDGEAI_DATABASE_URL`、PostgreSQL 进程、网络、权限和数据库名，修复后重新执行 setup。

任务执行返回 HTTP 503 和 `LANGGRAPH_CHECKPOINTER_NOT_READY` 时，不会降级到内存 checkpointer。确认健康状态，重新执行显式 Checkpointer setup，再重试新运行；不要通过启动参数绕过持久化要求。

持久化 API：

```text
POST /api/v1/tasks
GET  /api/v1/tasks
GET  /api/v1/tasks/{task_id}
POST /api/v1/tasks/{task_id}/runs
GET  /api/v1/tasks/{task_id}/runs
POST /api/v1/tasks/runs               # V0.2 兼容入口，同样写入 PostgreSQL
```

创建并执行任务：

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/tasks \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: create-local-001" \
  -d '{
    "title": "桥梁无人机影像质量检查",
    "task_type": "bridge_inspection",
    "objective": "检查桥梁无人机影像质量",
    "artifact_ids": ["art_001"]
  }'

curl -s -X POST http://127.0.0.1:8000/api/v1/tasks/<task_id>/runs
curl -s http://127.0.0.1:8000/api/v1/tasks/<task_id>/runs
```

建议使用 `python -m uvicorn`，这样可以确保调用的是当前虚拟环境中的 Uvicorn，而不是 Anaconda 或系统环境中的全局命令。

## 前端启动

安装前端依赖并启动：

```bash
npm install --prefix frontend
npm run dev --prefix frontend -- --host 127.0.0.1 --port 5173
```

工作台会从后端加载 PostgreSQL 任务和执行历史。每次执行都保存独立的模型 Profile、任务理解结果与 usage、Workflow 历史、Tool 输出、失败信息、`workflow_runtime` 和 `checkpoint_thread_id`；刷新浏览器或重启后端不会丢失记录。

## 业务历史与框架 checkpoint 的所有权

BridgeAI 业务表 `inspection_tasks` 和 `inspection_task_runs` 是面向 API 与工作台的历史来源，保存任务、运行编号、最终状态和可展示的执行快照。每次业务运行都使用 `checkpoint_thread_id=run_id`，因此两次运行的图状态不会混入同一 thread。

LangGraph 官方表只保存图的 checkpoint、channel value 和 pending write 等框架状态。应用不把这些表当作业务历史 API，也不把业务 JSONB 快照当作 LangGraph 恢复协议。

当前运行链路不是跨两套表的原子事务：进程若在 LangGraph 已写 checkpoint、但业务运行最终快照尚未提交时崩溃，两侧可能短暂不一致。本切片不提供 resume/retry、崩溃对账或孤立 checkpoint 清理；interrupts、异步 workers、streaming、Store、Memory 和 RAG 也延后实现。发生这类故障时先保留业务运行和 checkpoint 证据，再由后续 reconciliation 机制处理，不要手工把单侧数据伪造成完成状态。

## V0.2 联调验收

启动前后端后执行以下两次运行验收：

1. 创建一个桥梁巡检任务并连续执行两次，确认两次均为 `completed`、`workflow_runtime=langgraph`、`checkpoint_thread_id=run_id`，且 run ID/thread ID 不同。
2. 使用官方 `PostgresSaver.list()` 按两个 run ID 分别读取 checkpoint，确认每个 thread 至少有五个 checkpoint。
3. 在工作台选择该任务，确认执行历史按最新在前排列；分别切换两次运行，模型、Workflow、Tool、runtime 和 thread 快照随选择变化，Workflow 依次显示 `task_understanding`、`data_check`、`image_quality_check`、`completed`。
4. 刷新页面，确认两条业务历史仍在；只停止并重启后端，再刷新并重新选择任务，确认 runtime/thread 不变、`langgraph_checkpointer=ready`，两个 thread 的 checkpoint 数仍大于零。

## 数据库迁移文件

迁移文件位于：

```text
backend/app/repositories/postgres/migrations/0001_v0_2_skeleton.sql
backend/app/repositories/postgres/migrations/0002_task_history.sql
backend/app/repositories/postgres/migrations/0003_langgraph_runtime.sql
```

`0001` 创建最小任务表，`0002` 扩展任务字段并创建每次执行的历史表 `inspection_task_runs`，`0003` 增加 LangGraph runtime/thread 元数据、约束和唯一索引。官方 checkpoint 表由独立 setup 命令管理，不属于这些业务 SQL 迁移。

## Agent Model Profile

当前默认 Agent Model Profile 为：

```text
model_id=DeepSeek-V4-Flash-4bit
model_version=omlx-current
alias=omlx-deepseek-v4-flash
provider=omlx
runtime=openai-compatible
api_base_url=https://omlx.cpolar.cn/v1
timeout_seconds=60
is_stub=false
```

任务理解阶段会通过 OpenAI-compatible Model Gateway 调用该模型，模型理解结果、模型 Profile 和 usage 会随 Workflow 返回。API key 使用本地 `.env` 的 `BRIDGEAI_AGENT_API_KEY`，不要写入仓库。
